# Sentra Security & Operational Limitations

**Document Version:** 1.0.0  
**Effective Date:** 2026-11-08  
**Applicability:** All Sentra Platform Deployments (v0.1.0+)  

---

## 1. Fail-Closed Target Execution Boundary

1. **Untrusted Target Code Execution:** Under core architectural specifications (`ADR-0004`, `REQ-F12`), untrusted repository execution (including build scripts, procedural macros, unit tests, fuzz targets, and generated PoCs) remains **strictly disabled and fail-closed** by default on the host development machine (`FailClosedBackend`).
2. **Dedicated Disposable VM Requirement:** Target execution requires an explicitly provisioned disposable Linux VM worker (`ContainmentLevel::DisposableVm`) with strictly denied outbound network egress (`EgressPolicy::StrictlyDenied`). Docker Desktop or WSL2 running directly on the host development workstation does NOT satisfy this boundary.
3. **No Host Convenience Exceptions:** Sentra does not provide a convenience flag or option to run untrusted target code directly on the host machine. The one reviewed exception is opt-in CodeQL analysis in build mode `none` (`sentra codeql analyze`, [ADR-0011](adr/0011-opt-in-host-codeql-analysis.md)): CodeQL's extractors read and parse the untrusted code on the host, without building or running it. See section 9.

---

## 2. Platform & Toolchain Scope

1. **Host Platform Envelope:** The primary tested development and control-plane host platform is **Windows 11 x64** with MSVC and PowerShell 7. Linux x86_64 is validated via the Docker test runner. Other operating systems (macOS, BSD) and architectures (ARM64, RISC-V) remain untested and unsupported.
2. **Strict Wildcard Prohibition:** Per `EXTENSIONS.md`, target adapter capability claims must use exact 7-tuples. Any declaration specifying wildcards (`*`, `%`, `all`, `any`) fails closed with `WildcardProhibited`. No universal language or tool support is claimed.
3. **Kernel-Space and Native Ring-0:** Kernel drivers, kernel-space fuzzing, and Windows-native ring-0 execution are explicitly out of scope. Target profiles are restricted strictly to user-space applications.
4. **Links in Workspace and Store Paths:** Commands that establish a workspace boundary (among them `init`, `status`, `session`, `recover`, `audit`, `scan` and `diff`) check a workspace or `--database` path as given and do not resolve it first: if any directory in it, including a system directory above the workspace, is a symbolic link (on Windows also a junction or other reparse point), the path is refused with `invalid_workspace` or `invalid_storage_location` (exit 4), even when the link leads to an ordinary directory. On macOS `/tmp`, `/var` and `/etc` are such links (to `/private/tmp`, `/private/var` and `/private/etc`), so `/tmp/project` or a path under the default `$TMPDIR` (`/var/folders/...`) has to be given in its `/private/...` form, or relative to a working directory inside it. The MCP server's file tools resolve links in their launch root first, but `sentra_get_session_status` passes the launch root to the store unchanged and reports `session_status_failed` for such a root. On macOS and Linux this refusal is covered only by a CI test (`symlinked_ancestors_of_root_and_storage_are_rejected_on_unix`), for which no passing run has been recorded yet.

## 3. Host Administrator & Shared Host Boundary

1. **Host Administrator Trust Model:** The security architecture assumes that the local host operating system administrator account is not compromised. A malicious local administrator or process executing under the same user token with elevated privileges can inspect local process memory, modify NTFS file attributes, or access unencrypted local SQLite databases.
2. **Multi-User Shared Host Warning:** Sentra is designed for single-operator local control planes or isolated remote worker fleets. Running Sentra on a multi-user shared host without service credential boundaries does not provide hostile same-user protection.

---

## 4. Analytical Confidence & Verifier Independence

1. **Candidate Claims vs. Verified Facts:** Model and scanner outputs (including LLM inferences, SARIF imports, and advisory matches) are classified as *candidate claims*. Absence in a subsequent scan does not prove a vulnerability is fixed.
2. **Three-Tier Verification Invariant:** A patch candidate is only admitted as verified when all three independent conditions hold:
   - Original baseline tests fail on unpatched code.
   - Target tests pass on patched code.
   - All baseline regression test suites pass with zero regressions.
3. **Anti-Collusion & Independent Verification:** External model agents and automated patch authors cannot self-approve remediation proposals. All sensitive actions require explicit human operator admission (`HumanApprovalRequired`).

---

## 5. Storage Durability and File Modification Semantics

1. **Domain Immutability vs. Physical File Modification:** CLI inspection commands (`sentra status`, `sentra session show`) are domain-state read-only. However, opening SQLite databases under WAL mode triggers standard database recovery and truncation checkpoints (`PRAGMA wal_checkpoint(TRUNCATE)`), which may modify physical file bytes and timestamps. Writable storage permissions are required even for inspection.
2. **Unrecoverable Storage Corruption:** Corrupt storage files or orphaned WAL locks fail closed immediately (`storage_or_service_failure`, exit code 5) to preserve forensic bytes. Automatic repair or destructive overwrite is prohibited.

## 6. Web Console and Pinned Core Commands

1. **Web Console Scope:** The web console (`web/`) shows only data from the core CLI, read-only core stores, its own persisted history, GitHub, OSV.dev (opt-in) and configured model providers. Patch candidates are dry-run checked and never reported as verified, PR scans cover only changed files at the head commit, and webhook scans run against the local checkout. See [web/README.md](../web/README.md#limitations).
2. **Sample-Based, Local-Only and Unimplemented Core Commands:** The web console uses none of these commands as data sources.
   - `sentra audit`, `sentra propose-pr` and `sentra export sarif` match the packages of the lockfiles at the workspace root against a small advisory sample bundled with Sentra (6 hand-written records, curated 2026-11-08; reported as `advisory_db_source: "bundled_pinned_sample"`), not a synchronized OSV, RustSec or GHSA feed. A clean result says nothing about advisories outside the sample. Advisories are matched by package name (ASCII case-insensitive) and version only: the ecosystem is not compared, so a same-named package from another ecosystem can match. A lockfile that cannot be parsed is reported as not audited (`lockfiles_unparsed`) and its packages are skipped. The readers for `pnpm-lock.yaml`, `poetry.lock`, `go.sum`, `Gemfile.lock` and `requirements.txt` skip content they do not recognize instead of failing, so a malformed file of these kinds is listed as audited with only the entries that could be read (observed 2026-11-11 with deliberately malformed files on Windows 11 x64). The `yarn.lock` reader, which also reads the text form of `bun.lock`, rejects unindented lines that are not block headers and blocks without a version, so a file truncated inside a block is reported as not audited; it ignores indented lines it does not recognize, so a block that keeps its `version` line is read even when other lines are damaged.
   - `sentra sync-advisories` parses local OSV JSON in memory and reports the entries found (`persisted: false`). It reads a subset of the OSV schema: `introduced` and `fixed` range events, evaluated as semver-like ranges whatever the range type; `last_affected`, `limit`, the ecosystem and `withdrawn` are not used. Nothing is downloaded or stored and no other command sees the parsed records. `--database` fails with `not_implemented` (exit 5) because the store has no advisory table.
   - `sentra propose-pr` prints local draft pull request previews. No branch, commit or pull request is created, and the suggested `gh` command is not run (it needs the branch on the remote first, and the preview body saved as `<proposal_id>.md`, which it reads with `--body-file`; characters a shell could interpret are replaced with `_` in its title and branch). The diffs are illustrative version bumps that do not apply as-is, and each preview body marks reachability analysis and patch verification as not done. Each preview names the lockfile its package was read from; each lockfile is audited separately, so a package version listed by two lockfiles gives one finding and one preview per lockfile (with different proposal ids, but the same suggested branch name, since the branch is named after the advisory).
   - `sentra export sarif` contains the dependency audit results only; SAST results are written by `sentra scan --sarif`. Sentra does not upload SARIF anywhere, and acceptance of these files by GitHub Code Scanning has not been tested. `sentra codeql --sarif` reports the results of a CodeQL SARIF file as parsed candidate findings (`candidate_findings_parsed`) without storing or admitting them; `sentra codeql import` and `sentra codeql analyze` are described in section 9.
   - `sentra fleet` reports an empty registry (no persisted worker registry exists yet).
   - `sentra verify-audit` and `sentra config test` are not implemented: they exit 5 with `not_implemented`. There is no worker registry, secret-inheritance check or audit-trail tamper-evidence check to assess, and the core CLI has no model-provider client. The core `MultiUserSecurityAudit` reports gates with nothing to evaluate (an empty registry, no leasable worker) and gates 4 and 5 (secret inheritance, audit-trail tamper evidence) as not assessed, so it never returns `Approved`.
   - `sentra config show` and `sentra config set` store plain-text key/value rows in a `system_settings` table (values, API keys included, are not encrypted). No Sentra command reads them.
3. **Web Console Host and Tool Detection:** The host page reports whether a tool's file exists and whether its header says it can run on the host. It does not report the version, licence or whether the tool works. A tool path set in the console is checked the same way: Sentra never runs it, so a file that exists, has the right format and is executable may still not be the tool or may not work. It is checked again when it is saved and at each tool search refresh (about every 60 seconds), so a file removed or a drive that went offline in between is reported only after the next refresh; a path whose drive does not answer within the check deadlines is reported as not answering, not as missing. On Windows, the persisted PATH and the native architecture come from one `powershell.exe` registry read limited to 15 seconds: the first host-page response after the bridge starts can wait that long for it, and on a host where Windows PowerShell 5.1 does not answer in time (or is blocked), the persisted PATH is reported as not read and retried with backoff, and the architecture is taken from the process environment, which reports x64 for an x64 bridge emulated on Windows on Arm. Only Windows 11 x64 has been exercised on a real host. The macOS, Linux and Arm code paths (persisted PATH sources, emulation detection, memory sources) follow documented OS sources and are tested only with injected OS answers. The ownership check for running a persisted-PATH `gh` on macOS and Linux has a real-file-system unit test (temporary files and modes owned by the test user; ownership by another user is covered with injected values only), which runs only on POSIX hosts: the CI `web-test` job runs the bridge unit tests on `ubuntu-latest`, `windows-latest` and `macos-latest`, but no passing POSIX run has been recorded yet. Scoop shims are resolved through their `.shim` files; Chocolatey shimgen shims are not (the platform check reads the shim, not its target). On Windows, the ACLs of persisted-PATH directories are not checked before `gh` is run, and on no OS is the ownership of the file `SENTRA_GH_BIN` names checked (the host operator chose it). See [web/README.md](../web/README.md#host-and-tool-detection).
4. **Web Console Plugin Directory:** Without `SENTRA_PLUGIN_DIR`, the bridge uses the core's platform default plugin directory, which it resolves once per process: changing `SENTRA_PLUGIN_DIR`, `APPDATA`, `HOME` or `XDG_CONFIG_HOME` requires a bridge restart, and plugin listings reuse one core run for up to 15 seconds unless *Rediscover* is selected (probe and run never reuse a completed listing either; all three join a listing that is still running). A default directory on an NFS or SMB mount is not detected on macOS and Linux; on Windows, a mapped network drive or a link to a share is refused only when the host's `realpath` reports its UNC form, which has been tested with injected real paths only. The bridge does not check the ownership or permissions of the plugin directory, and adapters in it, a per-user default directory included, run unsandboxed on the bridge host when they are probed or run. The core's macOS and Linux default directories have not been exercised through the bridge on a real host. The real-binary plugin tests run only where a `sentra` binary has been built, so far a Windows 11 x64 host; the CI `web-test` job does not build the core and skips them. See [web/README.md](../web/README.md#plugin-directory).
5. **Plugin Adapter Process Trees (`sentra plugin probe`/`run`, console *Plugins* tab):** When a session ends, the core kills the adapter's process tree. On Windows a kill-on-close Job Object contains every descendant (only a descendant created before job assignment, or every descendant when the job cannot be created, is not contained). On Linux and macOS the core kills the adapter's process group and every process it finds in the process table (`/proc`, or `ps -E` on macOS) that is the unreaped adapter, carries the session's `CONTAINED_BY_SENTRA` environment value, or descends from either. A descendant that left the process group (`setsid` or `setpgid`, for example a child started with Node's `detached: true`) and was started without that variable, or whose environment cannot be read (for example after changing user), is found only through its parent and keeps running once its parent chain to the adapter has exited before the session ends. On macOS with System Integrity Protection (SIP) enabled, the kernel withholds the environment of a process whose code signature is restricted (`CS_RESTRICT`, as for Apple's own binaries such as `/bin/sh`) from `ps -E` (`sysctl_procargsx` in XNU's [`bsd/kern/kern_sysctl.c`](https://github.com/apple-oss-distributions/xnu/blob/main/bsd/kern/kern_sysctl.c), read 2026-11-11), so such a process is never recognized by the value and is found only through its parent; whether a given third-party binary (Bun, Node.js, a JDK) is restricted has not been checked. The value is not a secret: an unrelated process of the same user that carries it is killed too, and a process id can be reused between reading the table and the kill. Where `/proc` or `ps` cannot be read, and on other Unix systems, only the process group is killed. The Linux and macOS paths are covered by the plugin tests in the CI `test` job; no passing Linux or macOS run of them has been recorded yet, and GitHub-hosted macOS runners are reported to run with SIP disabled ([actions/runner-images#8162](https://github.com/actions/runner-images/issues/8162)), so a passing macOS run does not cover the restricted-signature case. See [docs/PLUGINS_GUIDE.md](PLUGINS_GUIDE.md#7-security-model-and-residual-risks).

## 7. MCP Server Approvals

1. **Approval Tickets Cannot Be Granted:** The MCP tool `sentra_request_approval` returns a ticket that exists only in the memory of that MCP server process (`persisted: false`, `authorized: false`) and is lost when the server exits. No operator grant path is exposed over MCP or the CLI, so a ticket requested over MCP cannot be approved, and no MCP tool performs an action that needs one.

## 8. Example Adapters

1. **Examples, Not Integrations:** The adapters in `examples/adapters` are never loaded implicitly. The Snyk example always reports the same sample vulnerabilities, the Ollama example returns a fixed sample patch when its local daemon does not answer, and both return placeholder evidence labels. See [examples/adapters/README.md](../examples/adapters/README.md).
2. **Semgrep Example Adapter:** It has only been tested with a stand-in `semgrep` executable (Windows 11, Python 3.14.8), not with a real Semgrep; its use of Semgrep options follows the Semgrep CLI reference. Its `strictly_denied` egress is kept by refusing registry and URL rules and disabling metrics and the version check, and is not enforced by the host. Findings are returned only as a text summary (the protocol has no structured findings field) and are neither stored nor admitted as evidence. See [its README](../examples/adapters/sentra-adapter-semgrep/README.md).

## 9. CodeQL Host Analysis and Import

1. **Opt-In, Licence Gate Only:** `sentra codeql analyze` runs an operator-installed CodeQL CLI on the host and refuses to start without `--accept-codeql-terms`. CodeQL is licensed under the GitHub CodeQL Terms and Conditions (`LICENSE.md` in the distribution), which limit use to open-source codebases, and automated analysis or CI to open-source codebases hosted on GitHub.com, unless the use is under a paid GitHub Advanced Security licence, and forbid making CodeQL available as a hosted solution for others. Sentra records the acknowledgement but cannot check open-source status, the licence held, or how a deployment is used. The flag is not an authorisation check: on the CLI, anyone who can run `sentra codeql analyze` on a host (an operator, a script or a coding agent with shell access) can pass it; only the web console puts the setting behind an administrator. See [ADR-0011](adr/0011-opt-in-host-codeql-analysis.md#licence).
2. **What "Target Code Not Executed" Covers:** Only `codeql database create --build-mode=none` is used, and only for actions, cpp, javascript, python and ruby. go and swift (no build mode `none`) and rust, csharp and java are skipped: their build-mode `none` extractors run project-controlled code (Cargo build scripts and procedural macros, `dotnet restore` of the project's MSBuild files and NuGet feeds, the project's Gradle wrapper or Gradle/Maven). This exclusion rests on static inspection of CodeQL 2.27.4 (no canary run yet) and must be re-checked when CodeQL is upgraded. `target_code_executed: false` does not mean that nothing reads the code: CodeQL's extractors parse it on the host, and the cpp, python, javascript and (on Windows) actions extractors start host compilers, the host Python, Node.js and PowerShell, which read project files.
3. **No Sandbox:** CodeQL runs with the privileges of the account that runs Sentra. Containment is limited to an allowlisted environment (no tokens or provider keys), temporary and home directories inside a per-run directory outside the workspace, `NoDefaultCurrentDirectoryInExePath=1` on Windows, `PYTHONDONTWRITEBYTECODE=1`, a `PATH` without relative entries or entries inside the workspace, a total time budget, and killing the process tree (Windows Job Object; Unix process group plus, on Linux and macOS, the processes found as described in [section 6, item 5](#6-web-console-and-pinned-core-commands)). Memory is limited only through CodeQL's own `--ram`; disk use and network egress are not limited. On Linux and macOS, a CodeQL process group keeps running when the `sentra` process itself is killed with a signal before its own timeout fires (a caller that uses `--cancel-on-stdin-eof` and closes the pipe instead gets the tree stopped first). A descendant that calls `setsid` leaves the group; on Linux and macOS it is still killed when it carries the step's `CONTAINED_BY_SENTRA` value (inherited unless a CodeQL component starts it with an environment without it; on macOS only where the kernel shows its environment, see section 6, item 5; not verified with a real CodeQL) or its parent is still alive, on other Unix systems it is not. On Windows, a workspace, `--work-dir` or `--pack-cache` path containing `&`, `^`, `!` or `%` is refused before CodeQL starts, because CodeQL's extractor batch scripts expand those paths unquoted (`set LGTM_SRC=%CD%`) and `cmd.exe` would run part of the path, or a file in the workspace, as a command; such workspaces need a copy under another path, or an imported SARIF. On Linux and macOS, `--work-dir` and `--pack-cache` must belong to the user and must not be writable by group or others (`unsafe_directory`), and the run directory is created new with mode 0700; directories above the work directory are not checked, so use a private location such as `~/.cache/sentra-codeql` rather than a shared `/tmp` path. Programs that look for executables in the current directory themselves (not through CreateProcess or `cmd.exe`) are not covered by `NoDefaultCurrentDirectoryInExePath`. On Windows, CodeQL's Java VM takes `user.home` from the account's real profile directory although `HOME` and `USERPROFILE` point into the run directory (verified with CodeQL 2.27.4 on 2026-11-11), so a per-user CodeQL configuration file there may still be read; caches stay out of it because every step passes `--common-caches`.
4. **Query Packs:** The CLI-only CodeQL distribution has no query packs. Packs are read from the distribution's `qlpacks/` or the `--pack-cache`; only `--allow-pack-download` lets `codeql pack download` fetch them (by default from `ghcr.io`), without credentials. Sentra neither pins pack versions nor verifies their digests, and the version CodeQL downloads may require a newer CLI. Without packs, `codeql_query_pack_missing` (exit 6) is returned.
5. **Real CodeQL Runs on Windows Only:** On 2026-11-11 `sentra codeql analyze` ran with CodeQL CLI 2.27.4 on Windows 11 x64 (ADR-0011 experiment E3): a JavaScript fixture was analyzed with 3 results and a Python fixture with 1, a Go file was skipped as needing a build, no `~/.codeql` was created and the run directories were deleted. Linux and macOS runs (E4), canary runs of the excluded extractors (E5) and resource use on large repositories (E6) are pending. `--search-path=<distribution>` does not stop CodeQL from searching the directories next to the distribution for a pack it cannot find: on a distribution installed directly under `D:\`, `codeql resolve qlpacks` did not finish within 90 seconds with or without it. Analyses stay fast only because Sentra runs a suite only when its pack is already present. Without `--ram` CodeQL chooses its own memory size; on a host short of free memory `codeql database analyze` failed (Java VM commit failure, Windows error 1455, or "CodeQL is out of memory"), and the same analysis with `--ram 2048` completed. `codeql pack download` depends on the host's connection to `ghcr.io`: on the test host the first download took about five minutes, and two later standalone attempts failed after about 300 seconds with "Connection timed out".
6. **Import:** `sentra codeql import` accepts CodeQL SARIF only (other tools: `sarif_not_codeql`), at most 64 MiB. The file is read into memory whole and then parsed in one streaming pass that keeps only the results that become findings; at most 1 000 runs (later runs are skipped and the findings marked truncated), 32 tool extensions and 4 000 rules per tool component are read, and results of rules beyond that have no rule metadata. Paths are checked lexically against the workspace (absolute paths, URIs with a scheme or drive letter and paths that leave the workspace are dropped and counted); whether the files exist is not checked. A result without a region is placed at line 1. Imported findings are the claims of whoever produced the SARIF.
7. **Fingerprints:** A finding's `fingerprint` is CodeQL's `partialFingerprints.primaryLocationLineHash`, joined with `|` to `primaryLocationStartColumnFingerprint` when present (else to `c` and the start column), so two results of one rule on one line stay distinct. The line hash covers the line's content, not the rule or the path, so two rules flagging the same line can share a fingerprint; consumers should key findings on rule, path and fingerprint together. Without a line hash, the fingerprint is a SHA-256 of rule id, path, start line and message. Fingerprints of findings stored before this format are different, so the first analysis or import after an upgrade resolves the old findings and stores them again.
8. **Web Console:** Host analysis is off by default; a SecurityAdmin enables it together with the terms acknowledgement, which the bridge records but cannot check against the codebase or the licence held. At most one analysis runs per bridge, and a scan that finds one running reports its own analysis as skipped instead of waiting. Cancelling a scan closes the core's standard input (`--cancel-on-stdin-eof`); the core then kills CodeQL's process tree and exits, and only then is the lock released. On Windows this was tested with a fake CodeQL (contract test), a stand-in core (bridge test) and, through the CLI, a real CodeQL 2.27.4 run (no process from the distribution was left 3 seconds after stdin closed); on macOS and Linux it is covered by the same contract test in CI but has not been run against a real CodeQL. If the core has not exited 30 seconds after its input was closed, the bridge kills it, and on macOS and Linux the current CodeQL step may then keep running after the lock is released. Earlier findings are resolved only for the rules a run or import ran (CodeQL lists every query it ran, also those without results): switching the query suite, or importing a SARIF of a narrower suite, leaves the findings of queries that no longer ran open, and a SARIF that lists no rules resolves only findings of the rules it reports results for. Each origin (host analysis, SARIF import, GitHub code scanning) is stored and counted on its own, so one CodeQL result reported by several origins counts once per origin in the open total, the severity counts, the heuristic risk score, the executive report and the SARIF export; the overview shows the count per origin. The SARIF import route streams the upload into a private file, parses uploads only up to 256 KiB in the bridge (larger ones only in the core), and processes one import at a time (`codeql_import_busy` otherwise). The scan stream sends a keep-alive comment every 15 seconds so reverse proxies do not close it during a long analysis; proxies with a read timeout below 15 seconds still do. The GitHub code scanning sync reads at most 1000 open alerts (one more page is read to tell whether more exist), matches their repository-relative paths to the workspace as they are, and has been tested with injected GitHub responses only. See [web/README.md](../web/README.md#codeql).
