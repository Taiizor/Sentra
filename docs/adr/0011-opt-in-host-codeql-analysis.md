# ADR-0011: Opt-In Host CodeQL Analysis (Build Mode `none`)

- Status: Accepted (2026-11-11, by the project maintainer). Narrowly and partially supersedes [ADR-0004](0004-vm-boundary-for-untrusted-execution.md) for the single case described below. Implemented in the core CLI (`sentra codeql analyze`, `sentra codeql import`) and the web console. Experiment E3 (a real CodeQL 2.27.4 run on Windows 11 x64) passed on 2026-11-11; the Linux and macOS runs and the other experiments listed at the end are pending. Updated 2026-11-11 after an operator report (Context, "Silent pack downloads"): progress events, `sentra codeql packs` and a separate pack download budget (points 7 and 8, "Progress reporting"), and after a real scan of the Sentra repository (Context, "TypeScript runtime and extraction scope"): a TypeScript runtime and path exclusions (point 10). These are tested with a fake launcher (E2) and, on Windows 11 x64, with CodeQL 2.27.4 (E7, partly done).
- Date: 2026-11-11
- Decision owner: Project maintainer

## Context

ADR-0004 keeps every real untrusted execution off the operator host and introduces no host execution exception "for convenience". Operators asked for CodeQL results in Sentra. Two separate needs exist:

1. Results that CodeQL already produced elsewhere: a local run, a GitHub Actions workflow, or GitHub code scanning alerts of a repository. Using them executes nothing.
2. Results that Sentra produces itself by running an operator-installed CodeQL CLI against a registered workspace, on the host that runs the Sentra core and web bridge, because no disposable VM worker exists yet (see [docs/RELEASE_GATES_AUDIT.md](../RELEASE_GATES_AUDIT.md)).

On 2026-11-11 the maintainer decided "both": result import is always available, and host analysis exists but is off by default, enabled by an administrator who explicitly acknowledges the CodeQL licence terms, and recorded by this ADR.

Facts observed on the development host (Windows 11 x64, build 10.0.26300) on 2026-11-11:

- CodeQL CLI 2.27.4 is installed at `D:\CodeQL`, a CLI-only distribution: it contains `codeql.exe` (PE launcher), `codeql.cmd`, the extension-less shell launcher `codeql`, `tools/`, `.codeqlmanifest.json` and one directory per extractor, but no `qlpacks/` directory, so no query packs. Analysis needs `codeql/<language>-queries` packs from the package registry (by default `ghcr.io`) or the CodeQL bundle, which ships them.
- Because the distribution sits directly under `D:\`, CodeQL warns about a root-level installation, and its default pack search, which includes the directories next to the distribution, scans the drive: `codeql resolve qlpacks` with default options did not finish within 2 minutes (observed during the tool-detection work before this ADR). An explicit search path does not turn this off: CodeQL's help says sibling directories "will always be searched for QL packs that cannot be found otherwise", and during E3 `codeql resolve qlpacks --search-path=D:\CodeQL` did not finish within 90 seconds either.
- Build modes declared by the extractors (`<language>/codeql-extractor.yml`): actions `none`; cpp `autobuild`, `manual`, `none`; csharp `autobuild`, `manual`, `none`; java `autobuild`, `manual`, `none`; javascript `none`; python `none`; ruby `none`; rust `none`; go `autobuild`, `manual`; swift `autobuild`, `manual`.

### Silent pack downloads

On 2026-11-11 an operator enabled host analysis in the web console (pack download allowed, no `--ram`, 4 threads, 30-minute timeout) and scanned the Sentra repository. The scan showed only the `sentra codeql analyze` command line and nothing else, and the operator cancelled it after about 15 seconds as not progressing. Diagnosis on the development host: the core first ran `codeql pack download codeql/<language>-queries` for each detected language in turn (javascript, python and actions; rust is skipped), one pack takes about five minutes on this host's connection (about 130 KB/s; a direct run had downloaded 78 MB in 10.6 minutes and was still on the third pack), CodeQL prints nothing while it downloads, and the bridge forwarded nothing, so the console looked frozen; cancelling killed the download and its partial pack. Earlier on the same host, CodeQL without `--ram` failed in `database analyze` because its Java VM could not commit memory (another program used about 17 GB).

### TypeScript runtime and extraction scope

On 2026-11-11 a real `sentra codeql analyze` of the Sentra repository on the development host failed for javascript: `codeql database create` exited with code 2 after 340 s, and CodeQL's log said "Could not start Node.js. It is required for TypeScript extraction. Please install Node.js and ensure 'node' is on the PATH." The host has no Node.js, and Sentra introduces no host JavaScript runtime other than Bun ([AGENTS.md](../../AGENTS.md)). The JavaScript extractor of CodeQL 2.27.4 reads `SEMMLE_TYPESCRIPT_NODE_RUNTIME` (strings in `javascript/tools/extractor-javascript.jar`; related: `SEMMLE_TYPESCRIPT_NODE_RUNTIME_EXTRA_ARGS`, `SEMMLE_TYPESCRIPT_TIMEOUT`, `SEMMLE_TYPESCRIPT_RETRIES`). With it set to Bun's `bun.exe` (Bun 1.4.4), CodeQL logged "Found Node.js at …bun.exe", "version 1.4.4" and "Memory for TypeScript process: 2048 MB", extracted `.ts` and `.tsx` files, a TypeScript Express fixture produced `js/reflected-xss`, and the Sentra repository's javascript database was built in 32 s.

The same scan also extracted rustdoc output (`target/doc/*.html`) and the built web console (`web/dist`). `--codescanning-config` with `paths-ignore` left them out, but made CodeQL resolve query packs, which with the distribution at `D:\` searched the drive for 265 s. `LGTM_INDEX_FILTERS` (`exclude:<glob>` lines separated by line breaks), which the javascript, python, ruby and actions extractors of 2.27.4 read (strings in their tools), left them out without that search: with `exclude:**/node_modules`, `exclude:**/target`, `exclude:**/dist` and `exclude:**/.git`, 348 files were extracted, none under `target/` or `web/dist`, database creation took 32 s and analysis 34 s (code-scanning suite, 0 results). The C/C++ build-mode-`none` driver `cpp/tools/win64/bmn.exe` contains `LGTM_INDEX_FILTERS`, `LGTM_INDEX_INCLUDE`, `LGTM_INDEX_EXCLUDE` and "Invalid filter in LGTM_INDEX_FILTERS"; on a two-file C fixture with `exclude:**/build` it reported "found 1 source files" and the database's source archive held only `src/main.c`, not `build/gen.c` (its `baseline-info.json`, a line count, still listed both).

### `none` does not mean "no project code runs"

Build mode `none` means CodeQL does not run a build. Static inspection of the 2.27.4 distribution on this host (strings in the extractor binaries and archives, and the extractor scripts; no extractor was run) shows that three `none`-mode extractors still run project-controlled code or project-selected tools:

| Language | Evidence (CodeQL 2.27.4, `D:\CodeQL`) | Consequence |
| --- | --- | --- |
| rust | `rust/codeql-extractor.yml` documents "internal cargo commands the extractor uses"; `rust/tools/win64/extractor.exe` contains "Running build scripts:", "Failed to run build scripts for" and the configuration keys `build_script_command` and `proc_macro_server`. | Cargo build scripts (`build.rs`) and procedural macros of the project run on the host. |
| csharp | `csharp/tools/win64/Semmle.Extraction.CSharp.DependencyFetching.dll` contains "Restoring project", "Restoring solution", "Using NuGet feeds from nuget.config files as fallback feeds" and a `nuget.exe` restore of `packages.config`; no extractor option disables it. | `dotnet restore` evaluates the project's own MSBuild files (which can run tasks) and fetches packages from feeds the project's `nuget.config` names. |
| java | `java/tools/autobuild-fat.jar` (`com/semmle/util/build/Gradle.class`) contains `./gradlew`, `--init-script`, "Downloading Gradle wrapper" and "Unable to run gradle to determine the project dependency graph because no gradlew or gradle binary is present"; `java/tools/` ships `java-buildless-maven-plugin.jar` and `dep-graph.gradle`. | The project's Gradle wrapper script, or Gradle/Maven evaluating the project's build files, runs to infer dependencies. |

The remaining `none`-mode extractors start helper programs too, which matters for the mitigations below:

- python: `python/tools/autobuild.cmd` runs `python` by name through `cmd.exe` with the source root as the current directory, and the extractor (`buildtools/index.py` in `python3src.zip`) runs `python -S -c "import gzip"` there unless `CODEQL_EXTRACTOR_PYTHON_ENABLE_SITE` is set. With `-c`, Python puts the current directory first on `sys.path`, so a `gzip.py` in the source root would be imported.
- actions (Windows): `actions/tools/autobuild.cmd` runs `powershell.exe -File` by name.
- cpp: `cpp/tools/win64/bmn.exe` searches for host compilers (vswhere/MSVC, clang, gcc) to read their default include paths; its dependency installation runs only when `CODEQL_EXTRACTOR_CPP_AUTOINSTALL_DEPENDENCIES` is set.
- javascript: the extractor installs dependencies only when `LGTM_INDEX_TYPESCRIPT_INSTALL_DEPS` is set. TypeScript is parsed by CodeQL's own wrapper (`javascript/tools/typescript-parser-wrapper`) under a JavaScript runtime: by default the host's Node.js, found on `PATH` (`extractor-javascript.jar`: "Please install Node.js and ensure 'node' is on the PATH."), or the program `SEMMLE_TYPESCRIPT_NODE_RUNTIME` names. Sentra neither installs nor uses Node.js; it passes Bun (point 10).

On Windows, the python and javascript extractors (and, through `actions/tools/autobuild-impl.ps1`, the actions extractor) run batch scripts through `cmd.exe` with the source root as the current directory, and those scripts expand paths without quotes: `python/tools/autobuild.cmd` and `javascript/tools/autobuild.cmd` contain `set LGTM_SRC=%CD%`, the Python script also `set LGTM_WORKSPACE=%CODEQL_EXTRACTOR_PYTHON_SCRATCH_DIR%` (a directory below the database, so below the work directory), and the JavaScript script `set SEMMLE_DIST=%CODEQL_EXTRACTOR_JAVASCRIPT_ROOT%` (inside the distribution). `cmd.exe` treats `&` in the expanded value as a command separator. On 2026-11-11, on this host, a scratch copy of that line run with the working directory `ws&echo INJECTED-BY-DIRNAME&rem x` printed `INJECTED-BY-DIRNAME`; a reviewer also reproduced that a workspace below a directory named `R&D` made `cmd.exe` run `D\app.cmd` from the workspace with `NoDefaultCurrentDirectoryInExePath=1` set (a relative command containing a backslash is resolved against the current directory). `^` (escape), `!` (delayed expansion is on in the JavaScript script) and `%` also change such a line. The Linux and macOS scripts (`autobuild.sh`) quote these values (`LGTM_SRC="$(pwd)"`).

On Windows, a program started by a bare name is looked up in the current directory of the starting process first. On 2026-11-11, on this host, a Python 3.14.8 process whose current directory contained `sentraprobe.exe` (a copy of `hostname.exe`) started it with `subprocess.run(["sentraprobe"])` (CreateProcess); with `NoDefaultCurrentDirectoryInExePath=1` in its environment the same call failed with "file not found", and `cmd /c sentraprobe` behaved the same way. CodeQL starts its extractor scripts with the source root as the current directory.

### Licence

The CodeQL CLI is not open source. Its terms are in `LICENSE.md` at the top of every CodeQL distribution ("GitHub CodeQL Terms and Conditions"). Quoted from the 2.27.4 copy on this host:

- "The Software is licensed on a per user basis."
- Use rights that do not depend on the codebase: "Use the Software to perform academic research.", "Use the Software to demonstrate the Software." and testing OSI-licensed CodeQL queries.
- "Here's what you may also do with the Software, but only with an Open Source Codebase [...]: Perform analysis on the Open Source Codebase. If the Open Source Codebase is hosted and maintained on GitHub.com, generate CodeQL databases for or during automated analysis, CI, or CD."
- Restrictions: the terms do not authorize use "To otherwise or in any other context generate any CodeQL database for or during automated analysis, CI or CD" or "in connection with any codebase that is not an Open Source Codebase (e.g., code in a private repo in GitHub)".
- "if your use of the Software is under a paid customer license for GitHub Advanced Security, the restrictions with respect to automated analysis, CI, and CD and use in connection with non-Open Source Codebases do not apply."
- You may not "share, publish, distribute or lend the Software, provide or make available the Software as a hosted solution (whether on a standalone basis or combined, incorporated or integrated with other software or services) for others to use".

Sentra cannot determine whether a workspace is an Open Source Codebase, whether the operator holds a GitHub Advanced Security licence, or whether a multi-user web console deployment counts as making CodeQL available "as a hosted solution [...] for others to use". These are the operator's decisions (ADR-0007: "Keep CodeQL optional and entitlement-aware").

The query packs (`codeql/<language>-queries` and the library packs they bundle) are developed in the github/codeql repository, whose [`LICENSE`](https://github.com/github/codeql/blob/main/LICENSE) is the MIT License ("Copyright (c) 2006-2025 GitHub, Inc.", read 2026-11-11). The packs downloaded on this host (`javascript-queries` 2.5.0 and `python-queries` 1.9.0, `cliVersion: 2.27.4` in their `qlpack.yml`) contain no licence file, and their `qlpack.yml` names no licence; the MIT statement therefore rests on the source repository, not on the downloaded artefact. Downloading them is done by the CodeQL CLI (`codeql pack download`), so the CLI's terms above govern that use of the CLI. Sentra design judgment: `sentra codeql packs --download` does not require `--accept-codeql-terms`, because it creates no database and analyses no codebase; it still runs the CodeQL CLI, and whether that use is covered remains the operator's assessment.

## Alternatives

1. Import only: no CodeQL execution by Sentra. Safe, but every operator needs a separate pipeline.
2. Run CodeQL on the host in any build mode. Builds and build tracing execute project code; rejected by ADR-0004.
3. Run CodeQL only inside the disposable VM worker of ADR-0004. Correct boundary, but no worker exists yet.
4. Run CodeQL on the host, off by default, in build mode `none` only, for languages whose extraction does not run project-controlled code, with process containment and an explicit licence acknowledgement.

## Decision

Choose option 1 for imports, always available, and option 4 for host analysis. Option 3 remains the target; when a worker exists, host analysis should move into it.

**Import (no execution).** `sentra codeql import --sarif <file> --workspace <dir>` normalises CodeQL SARIF produced elsewhere. Documents over 64 MiB (`sarif_too_large`), invalid JSON (`sarif_invalid`) and runs whose `tool.driver.name` is not `CodeQL` (`sarif_not_codeql`) are rejected; results whose path is absolute, has a scheme or drive letter, or leaves the workspace after `.`/`..` resolution are dropped and counted. The document is read in one streaming pass: runs are processed one at a time, only results that become findings (at most `--max-results`) are kept, and at most 1 000 runs, 32 tool extensions and 4 000 rules per tool component are read, so memory follows the kept findings rather than the number of elements (measured on this host on 2026-11-11 with a release build: a 64 MiB file of 22.3 million empty results peaked at 98 MB of private memory, and a 4.2 MB file of 1.4 million at 14 MB, where the previous typed parser needed 706 MB for the 4.2 MB file). Each language lists the rules the SARIF ran (CodeQL lists every query it ran, also those without results), so a consumer can resolve earlier findings of exactly those rules; a finding's fingerprint is `primaryLocationLineHash` joined with `primaryLocationStartColumnFingerprint` (or the start column), so two results of one rule on one line stay distinct. The web console's import uses this contract. Its read-only GitHub code scanning alert sync does not: the bridge maps GitHub's REST alerts itself (severity from `rule.security_severity_level` or `rule.severity`, identity from the repository and alert number; see [web/README.md](../../web/README.md)).

**Host analysis (opt-in).** `sentra codeql analyze` runs only when all of the following hold:

1. **Licence gate.** The caller passes `--accept-codeql-terms`; otherwise the CLI fails with `codeql_terms_not_accepted` before touching the file system. The flag is a licence acknowledgement, not an authorisation check: anyone who can run `sentra codeql analyze` on a host (an operator, a script, or a coding agent with shell access) can pass it, so on the CLI host analysis is as available as the `codeql` program itself. In the web console, analysis is disabled by default and an administrator enables it in the same request that records the terms acknowledgement; console users cannot pass the flag themselves.
2. **Launcher.** `--codeql` must be the `codeql` program of a CodeQL distribution: on Windows `codeql.exe` with a PE header (`codeql.cmd`, `.bat` files and the shell launcher are refused); on Linux and macOS the executable file named `codeql`, which is the distribution's shell launcher. Its directory must contain `tools/` and `.codeqlmanifest.json` or a `<language>/codeql-extractor.yml`. Otherwise `codeql_not_found`.
3. **Build mode `none` only.** Every database is created with `codeql database create <db> --language=<id> --build-mode=none --source-root=<workspace>`. Sentra has no code path that passes `--command`, `autobuild`, `manual` or tracing options.
4. **Language allowlist.** actions, cpp, javascript, python and ruby are analysed. go and swift are skipped ("requires building the project, which Sentra does not do on the host"), and so are rust, csharp and java, with reasons naming the project code their `none`-mode extractors run (table above). A language whose extractor is missing from the distribution, or does not declare `none`, is skipped too.
5. **Directories.** `--work-dir` and `--pack-cache` must be outside the workspace (`work_dir_inside_workspace`, `pack_cache_inside_workspace`); the check follows links of the nearest existing ancestor before anything is created. Each run gets a new run directory in the work directory, which is the working directory of every CodeQL step and holds the databases, the SARIF files and the redirected temporary and home directories. The run directory must not exist yet (it is never reused). On Linux and macOS it and its subdirectories are created with mode 0700, directories Sentra creates for `--work-dir` and `--pack-cache` get mode 0700 too, and an existing work directory or pack cache must belong to the current user and must not be writable by group or others (`unsafe_directory`): otherwise another local user could rename the run directory and put their own in its place before the extractors start, and the host Python, which reads `.pth` files from the user site below the redirected `HOME`, would run their code (a reviewer reproduced this mechanism on this host on 2026-11-11: with `HOME` and `APPDATA` redirected to a scratch directory, the host Python ran a `.pth` file planted there), or swap the SARIF or query packs. The user id is read from a file created in the work directory through its open handle, so a concurrent rename cannot change it. On Windows, a workspace, work directory or pack cache whose path contains `&`, `^`, `!` or `%` is refused before CodeQL starts (`invalid_workspace`, `unsafe_directory`), and so is a distribution directory containing one (`codeql_not_found`), because CodeQL's extractor batch scripts expand these paths unquoted (Context). The run directory is deleted after the run, also after a failure, timeout or cancellation.
6. **Environment.** Only `PATH`, `PATHEXT`, `SystemRoot`, `SystemDrive`, `windir`, `ComSpec`, `PROCESSOR_ARCHITECTURE`, `NUMBER_OF_PROCESSORS`, `LANG` and `LC_ALL` are copied from the caller; `PATH` loses relative and empty entries and entries inside the workspace. `TEMP`, `TMP`, `TMPDIR` and `HOME` (on Windows also `USERPROFILE`, `APPDATA` and `LOCALAPPDATA`) point into the run directory. `NoDefaultCurrentDirectoryInExePath=1` (Windows), `CODEQL_EXTRACTOR_PYTHON_ENABLE_SITE=1` and `PYTHONDONTWRITEBYTECODE=1` are added, and, from validated input only, `SEMMLE_TYPESCRIPT_NODE_RUNTIME` and `LGTM_INDEX_FILTERS` (point 10). The last one was added after E3: the host Python started by the Python extractor wrote `python/tools/__pycache__/python_tracer.cpython-314.pyc` into the CodeQL distribution; with it, a repeated run wrote nothing there. Tokens (`GITHUB_TOKEN`, `GH_TOKEN`), provider keys, `SENTRA_*`, `CODEQL_*`, `SEMMLE_*`, `LGTM_*`, `JAVA_TOOL_OPTIONS` and every other variable are not passed.
7. **Time and process tree.** Two budgets bound the steps: `--timeout-secs` (default 1800 s) covers the checks before the first step, `codeql version` (also capped at 120 s), `database create` and `database analyze`, and `--download-timeout-secs` (default 1800 s) covers all `codeql pack download` steps together; time spent downloading does not count against `--timeout-secs`. When the download budget runs out, the running download's tree is killed and its language fails with that reason, later downloads are not started, and languages whose packs are present are still analysed (`codeql_failed` only when no language was analysed). Each step runs under the plugin host's process containment (`run_contained_cancellable` in `crates/sentra-core/src/plugin/process.rs`): on Windows a kill-on-close Job Object, elsewhere a new process group (on Linux and macOS also a per-step `CONTAINED_BY_SENTRA` environment marker and a process-table scan for marked processes and descendants; see `docs/LIMITATIONS.md` section 6, item 5). When a step ends, normally or not, whatever it left running is killed; when the analysis budget runs out, the whole tree is killed and the command fails with `codeql_timeout` (partial results are discarded). With `--cancel-on-stdin-eof` the analysis is cancelled when the core's standard input reaches end of file: the running step's tree is killed and the command fails with `codeql_cancelled`. The web bridge keeps that pipe open while it waits and closes it to cancel a scan, so on Linux and macOS, where a signal to the core would not reach CodeQL's separate process group, the tree stops before the bridge releases its one-analysis lock; the pipe also closes when the bridge process dies. Captured stdout and stderr are bounded to 16 KiB each (256 KiB for `codeql version`, whose JSON must stay complete).
8. **Query packs.** Packs are used from the distribution's `qlpacks/` (preferred, it matches the CLI) or from `<pack cache>/packages/`. Sentra checks that `codeql/<language>-queries` and the suite file (`<language>-code-scanning.qls` or `<language>-security-extended.qls`) are present before CodeQL resolves anything, and passes the suite file by absolute path with `--search-path=<distribution>` and `--common-caches=<pack cache>`, so CodeQL never has to look for a missing pack next to the distribution, and the user's `~/.codeql` cache is not used. What keeps CodeQL from searching the drive is that the pack is present (a downloaded query pack carries its library dependencies, and the CodeQL bundle carries all of them), not `--search-path`, which does not disable the search next to the distribution (see Context and E3). Only with `--allow-pack-download` does `codeql pack download codeql/<language>-queries` run first, one pack per step, retried once after a non-zero exit (not after a timeout or cancellation). CodeQL 2.27.4 unpacks a pack straight into its final directory in `--common-caches` (`PackageRegistry.installPackage` and `PackageArchive.unzipArchive` in `codeql.jar`, read with `javap`: no staging directory, no rename), so a download killed while unpacking would leave a partial pack that CodeQL takes as installed once `qlpack.yml` exists (it then skips the download as already installed) or refuses to download over before that ("not empty and is not a package"). Each attempt therefore passes `--common-caches=<pack cache>/.sentra-staging-<pid>-<nanos>`, a new private directory; after exit code 0 the core renames every `packages/<scope>/<name>/<version>` directory with a `qlpack.yml` from it into `<pack cache>/packages/` (one rename on the same volume, replacing an unusable directory of the same version), and it deletes the staging directory after every attempt, whatever the outcome. A download that the remaining budget leaves no time for is not started and is reported as such. Otherwise the language is skipped, and the command fails with `codeql_query_pack_missing` when no language could run. `sentra codeql packs --codeql <launcher> --pack-cache <dir>` reports, per language, whether the pack and the suite file are present (in the distribution or the pack cache, with version, location and size) or missing, and which languages are not analysable and why, without running a program; with `--download` it runs the same download step for each missing pack of an analysable language, within `--timeout-secs` for all of them, so packs can be fetched ahead of a scan. It applies the launcher rules (point 2), the environment allowlist (point 6, with `PATH` filtered for relative entries only, since there is no workspace), the Windows refusal of a pack cache path containing `&`, `^`, `!` or `%` and the Unix ownership checks (point 5), process-tree containment and `--cancel-on-stdin-eof` (point 7); its run directory is created new inside the pack cache and deleted afterwards. A failed download returns `codeql_pack_download_failed` with CodeQL's message (control characters removed, at most about 600 characters per pack) and the state of every language; packs downloaded before stay in the cache. It needs no `--accept-codeql-terms` (Licence).
9. **Results.** SARIF is normalised as for imports; `target_code_executed` is always `false` in the result, in the sense defined by this ADR (no build, no build tracing, none of the three excluded extractors). Findings are candidate claims (ADR-0006) and the CLI stores nothing.
10. **TypeScript runtime and extraction scope.** `--typescript-runtime <path>` names the JavaScript runtime that CodeQL's JavaScript extractor parses TypeScript with (`SEMMLE_TYPESCRIPT_NODE_RUNTIME`). It must be an absolute local path (on Windows no UNC or device path) of an existing native executable outside the workspace (Windows: a `.exe` with a PE header and no `&`, `^`, `!` or `%` in the path; Linux and macOS: an ELF or Mach-O file with an execute bit; scripts are refused); otherwise `invalid_typescript_runtime` (exit 4) before CodeQL starts. Without the flag the core uses the first `bun` (`bun.exe` on Windows) in the absolute `PATH` entries outside the workspace that passes the same checks; without one it leaves CodeQL's default (`node` on `PATH`) and adds a warning when javascript is analysed. The web console passes the Bun executable it runs on, unless that executable lies inside the workspace being scanned (which the core refuses); it then passes none, and the core searches `PATH` as described. `--exclude <glob>` (repeatable, at most 50, checked by the core, so a 51st is `invalid_exclude` too; relative to the workspace, `/` as separator, no `..` segment, no `:`, no control characters, at most 200 characters; otherwise `invalid_exclude`, exit 4) becomes one `exclude:<glob>` line of `LGTM_INDEX_FILTERS`; the web console's default is `**/node_modules`, `**/target`, `**/dist` and `**/.git`. `--codescanning-config` is never passed, because it makes CodeQL resolve query packs (Context).

**Progress reporting.** With `--progress`, `sentra codeql analyze` and `sentra codeql packs` print one JSON object per line on stderr while they run: `{"progress": true, "event", "step", "language", "pack", "elapsed_ms", "duration_ms", "message"}`, where `event` is `step_started`, `step_finished`, `step_failed`, `heartbeat` or `language_skipped`, and `step` is `version`, `pack_download`, `database_create`, `database_analyze` or `null` (`language_skipped`). A heartbeat is sent every `--heartbeat-secs` (default 15) while a step runs, from the thread that waits for CodeQL. Without `--progress` the output is unchanged; with it, stdout and the final error object (the last stderr line, without a `progress` key) are unchanged. Messages are Sentra's own text plus, for failures, the same bounded CodeQL excerpt as `languages[].reason`. The web console streams these events into the scan log (web/README.md).

**Memory default in the web console.** The core passes `--ram` only when it is given. When no RAM limit is configured, the web console passes `--ram` set to half the host's available memory as shown on its host page, clamped to 1024–8192 MiB, and says so in the stage message, including when that reading is only `os.freemem()` because `MemAvailable` (Linux) or `vm_stat` (macOS) could not be read (on macOS it then counts only free pages); a fixed 2048 MiB is used only when even `os.freemem()` fails; a configured value wins (web/README.md). This follows the E3 failures without `--ram` (Security review) and the out-of-memory failure in the operator report above. On 2026-11-11 the bridge, run in-process against the real core, passed `--ram 7419` (half of 14 839 MiB available) and named the value and the rule in the stage message (E7).

This ADR supersedes ADR-0004 only for points 1 to 10 above. It does not authorise builds, tests, PoCs, other build modes, other scanners or plugins, other languages, or any other host execution; those remain under ADR-0004.

## Security review

| Threat | Mitigation | Residual risk |
| --- | --- | --- |
| A hostile workspace exploits a CodeQL extractor or parser (Java, native extractors, Python tracer, TypeScript wrapper) to run code on the host. | Off by default; administrator opt-in; per-run directories; allowlisted environment without credentials; time budget and tree kill. | Not contained: CodeQL runs with the privileges of the account running Sentra, without a sandbox, memory limit enforced by Sentra or network egress control. An extractor exploit has the same reach as that account. This is the main reason the decision is narrow and opt-in. |
| Project code runs through extractor helpers (build scripts, dependency restore, wrapper scripts, `gzip.py`). | Build mode `none` only; rust, csharp and java excluded; `CODEQL_EXTRACTOR_PYTHON_ENABLE_SITE=1`; dependency-installation switches of the cpp and javascript extractors are never set. | The exclusions rest on static inspection of 2.27.4. A later CodeQL version can add helpers to an allowed extractor; the allowlist is static and must be re-checked on CodeQL upgrades (experiment E5). |
| A workspace path (or a work directory, pack cache or distribution path) containing `&` makes `cmd.exe` run part of the path, or a file in the workspace it names, as a command when CodeQL's Windows extractor scripts expand it unquoted (`set LGTM_SRC=%CD%`). A workspace registered at a subdirectory of a hostile repository can choose the whole payload. | Windows: such paths are refused before CodeQL starts (`&`, `^`, `!`, `%`; Context, point 5); contract test with a workspace below `R&D`. | Other cmd.exe parsing quirks of future CodeQL scripts are not covered; the scripts must be re-checked on CodeQL upgrades (E5). Paths with these characters cannot use host analysis on Windows; their results can be imported. |
| Another local user replaces the run directory, the SARIF or the query packs through a shared work directory (Linux, macOS). | Run directory created new with mode 0700; work directory and pack cache must belong to the user and not be group- or world-writable (point 5). | Directories above the work directory are not checked; a parent another user controls can still be renamed (the check covers the work directory, which is the parent of the run directory). |
| A program planted in the source root is started by name from an extractor script. | `NoDefaultCurrentDirectoryInExePath=1` on Windows (verified for CreateProcess and `cmd.exe`, see Context); `PATH` without relative entries or entries inside the workspace on every platform. | Programs that search the current directory themselves, outside CreateProcess and `cmd.exe`, are not covered. |
| Host software started by CodeQL reads project files: host compilers (cpp), the host Python (python), the JavaScript runtime that runs CodeQL's TypeScript parser (javascript: Bun as Sentra passes or finds it, else Node.js on `PATH`), PowerShell (actions on Windows, which loads the operator's PowerShell profile). | They are the operator's installed programs, started by CodeQL, not by the project. | Their own parsers are exposed to project files; with `CODEQL_EXTRACTOR_PYTHON_ENABLE_SITE=1` the host Python's site initialisation runs. |
| The TypeScript runtime is a program the workspace or another user chose (a `bun` planted in the workspace or a relative `PATH` entry, a script, a network path). | `--typescript-runtime` and the `bun` found on `PATH` must be absolute, local, native executables outside the workspace, without cmd.exe metacharacters on Windows (point 10); `PATH` entries that are relative or inside the workspace are not searched; the variable is never inherited. | The runtime runs CodeQL's TypeScript parser over untrusted files with the account's privileges, like Node.js would. Bun is not Node.js: its compatibility with CodeQL's parser wrapper was verified only with CodeQL 2.27.4 and Bun 1.4.4 on Windows (Context), and a later CodeQL may need Node.js-specific behaviour. The automatically found `bun` is the first on `PATH`, which may not be the one the operator meant; pass `--typescript-runtime` to choose. |
| Exclusion globs hide code from analysis. | They are operator settings, validated as relative globs and passed only through `LGTM_INDEX_FILTERS`. | A broad glob (for example `**/*.js`) silently removes code and its findings; Sentra does not report which files were left out. Whether a future CodeQL version keeps honouring `LGTM_INDEX_FILTERS` is not guaranteed; the C/C++ driver honoured it on one fixture only (Context). |
| Resource exhaustion: huge or pathological sources, decompression bombs, deep nesting. | Total time budget; `--threads` and `--ram` passed to CodeQL; bounded captured output; run directory deleted. | Disk use of databases is not bounded; memory is bounded only as far as CodeQL honours `--ram`. Without `--ram` CodeQL chooses its own memory size: during E3, on a host with about 5.7 GB of free commit memory, `codeql database analyze` failed (Java VM `os::commit_memory` failure, Windows error 1455; on another run "CodeQL is out of memory", exit 99), and succeeded with `--ram 2048`. The core names this failure in the language's reason. |
| Query pack supply chain: a malicious or substituted pack from the registry. | Downloads only with `--allow-pack-download` or `sentra codeql packs --download`, and only into the explicit pack cache; no registry credentials are passed (anonymous download of public packs). | Sentra does not pin pack versions or verify digests; it relies on CodeQL's registry client and TLS. `codeql pack download` takes the version CodeQL selects, which may need a newer CLI. Sentra checks only that `qlpack.yml` and the suite file exist, not that a pack is complete. Its own downloads reach the pack cache only complete (staging directory, point 8); a pack directory made incomplete by anything else is still taken as present. |
| A long silent step (a pack download takes minutes and CodeQL prints nothing) is taken for a hang and cancelled, or a hung step is taken for a slow one. | `--progress` events for every step, skip and download, with a heartbeat while a step runs; separate download budget; `sentra codeql packs --download` to fetch packs ahead of a scan. | A heartbeat shows that the step's process is alive, not that it advances: CodeQL reports no progress Sentra reads, so a stalled download is only ended by its budget. A caller that does not read stderr while the command runs can block the progress writes and with them the timeout and cancellation checks. |
| Secrets: tokens in the environment; files readable by the account; links in the workspace pointing outside it. | Allowlisted environment; results located outside the workspace are dropped; the run directory (including the database's source archive) is deleted. | CodeQL can read any file the account can read, and may follow links in the workspace into the source archive while the run lasts. |
| Orphaned processes and leftovers. | Job Object (Windows) and process group (Unix; on Linux and macOS also marked processes and descendants found in the process table) killed after every step; run directory deleted; `--cancel-on-stdin-eof` lets a caller stop the tree by closing a pipe, and the tree also stops when that caller dies (point 7). | Unix: if the `sentra` process itself is killed with a signal (for example by a caller's own timeout without `--cancel-on-stdin-eof`, or after the bridge's 30-second grace period) the CodeQL process group keeps running, and a descendant that calls `setsid` leaves the group (on Linux and macOS it is still killed while it carries the marker, on macOS only where the kernel shows its environment, or while its parent is alive; see `docs/LIMITATIONS.md` section 6, item 5). Windows: a descendant created before job assignment is not contained. The run directory stays behind when `sentra` is killed. |
| The user's CodeQL configuration changes behaviour. | `HOME`/`USERPROFILE` point into the run directory; `--common-caches` is explicit. | Programs that resolve the profile directory from the OS rather than the environment may still read a per-user CodeQL configuration file. Verified for Java on Windows during E3: with `HOME` and `USERPROFILE` redirected, CodeQL 2.27.4's Java VM reported `user.home` as the account's real profile directory (`-J=-XshowSettings:properties`). No `~/.codeql` was created during E3, because every step passes `--common-caches`. |
| Licence non-compliance. | Explicit acknowledgement gate; terms quoted here and shown by the web console; `LICENSE.md` of the installed distribution is the authoritative text. | Sentra cannot verify open-source status, a GitHub Advanced Security licence, or whether a deployment is a hosted solution for others. |
| Crafted SARIF in imports: wrong tools, escaping paths, and documents built to inflate memory (millions of empty results, rules or locations). | 64 MiB cap; streaming parser that keeps only the results that become findings and the first rules, extensions, locations and tags; properties read into fixed fields; CodeQL driver check; lexical path confinement; bounded strings, tags and warnings. The web bridge streams the upload into a private file, parses only uploads up to 256 KiB itself, and processes one import at a time. | Imported findings are claims of whoever produced the SARIF. The core still reads the whole file (up to 64 MiB) into memory before parsing it. |

## Consequences

Operators can see CodeQL results without a separate pipeline, at the cost of running a large third-party analyser on the host against untrusted code. Rust, C#, Java, Go and Swift workspaces get no host analysis; their CodeQL results can be imported. Analysis needs query packs (the CodeQL bundle, or `--allow-pack-download`), which a CLI-only installation such as the one on this host lacks. Install CodeQL in a subfolder (for example `D:\Tools\codeql\` or `/opt/codeql/codeql/`), not directly below a drive or file-system root: CodeQL commands that resolve packs (`codeql resolve qlpacks`, a `--codescanning-config` file, a query by pack name) also search the directories next to the distribution, which below a root means the whole drive (Context). Sentra avoids those commands and warns when the distribution sits below a root, but other tools on the host may not.

## Validation and reversal

The contract tests (E2) run in `cargo test --workspace`. Reverting to option 1 removes `sentra codeql analyze` and the web console's analysis setting; imports are unaffected. Extending host analysis to another language, build mode or tool requires a new security review and ADR; a model, plugin or web request cannot widen it. Within this ADR's scope the CLI runs host analysis for whoever can start it with `--accept-codeql-terms` (point 1); limiting who may do that on a host is an operating-system matter, not something this flag provides.
