## [0.3.0] - 2026-11-11

### Added
- GitHub Actions CI workflow covering Linux, Windows, and macOS multi-OS test matrix.
- GitHub CodeQL static analysis workflow for JavaScript/TypeScript, GitHub Actions, and Rust.
- Automated PR scope labeler (`actions/labeler@v5`) and declarative label synchronizer.
- Dependabot configuration for Cargo, GitHub Actions, and Web npm packages.
- Cross-platform POSIX filesystem boundary and inode-based pinning in `sentra-core`.
- `sentra sync-advisories`: parses local OSV JSON (a subset of the OSV schema) in memory and reports the advisory entries found; nothing is downloaded or persisted, and the other commands keep using the bundled advisory sample.
- Pure-Rust SAST scanner with 10 high-precision secret and code antipattern rules (`sentra scan`).
- Multi-ecosystem lockfile support: npm, Yarn, pnpm, Bun, Deno, and Cargo (`sentra audit`).
- Web operations dashboard built with React 19, TypeScript, Bun, Tailwind CSS v4, and shadcn/ui.
- `sentra inventory`: read-only, recursive lockfile inventory with OSV ecosystem names.
- `sentra scan --file-name <name>` for snippet and stdin scans (selects language rules; replaces the fixed `sample.ts` label).
- `sentra patch apply --dry-run` and the `patch_does_not_apply` error code.
- `PatchApplied` / `PatchRolledBack` core audit events recorded through the persistence repository when `--database` is given.
- `sentra install mcp amp`: Sourcegraph Amp is its own MCP target (`amp.mcpServers` in `.amp/settings.json` or `~/.config/amp/settings.json`).
- `sentra install ... --mcp --command <path>` overrides the registered executable; by default the absolute path of the running `sentra` binary is registered.
- `sentra mcp [--workspace <dir>] [--database <file>]`: the MCP server's tools are confined to the workspace, and `--database` enables persisted session status.
- Bundled skills now ship every supporting file (references, scripts, rules) and their upstream `LICENSE`; NOTICE lists source, commit and license for each skill. `sentra skills show --json` lists the files.
- `sentra plugin list` reports discovery diagnostics (invalid manifests, duplicate ids, missing directories) and which manifest limits are enforced; `plugin run` reports the host-observed process exit code and the workspace sent to the adapter.
- Web console: tool detection on the *Host & workers* page searches the bridge process PATH, the persisted PATH (Windows registry system and user `Path`, macOS `/etc/paths` and `/etc/paths.d`, Linux `/etc/environment`) and standard install locations, where it used to search the process PATH only. Each tool row reports where the tool was found, whether the bridge process can see it, later (shadowed) matches, a symlink or junction target (not a mere 8.3 short-name or drive-letter expansion) or Scoop shim target, whether the file can run on this host (read from its PE, ELF or Mach-O header, universal binaries and scripts included; a file built for another OS or architecture is marked "found, but built for another platform — cannot run here"), and how the bridge uses it (`gh` executed, `bun` runtime, `codeql` presence only unless CodeQL host analysis is enabled, then executed through the core; the rest not used). Tools are never run to detect them. The same file reached through symlinked directories is reported once, and skipped UNC and device `PATH` entries are counted. A tool found outside the process PATH comes with an explanation for the host OS (Windows: the bridge's environment predates the `PATH` change; macOS: launchd does not apply `/etc/paths` or shell profiles; Linux: systemd and cron do not apply `/etc/environment` or shell profiles) and what to change. See web/README.md.
- Web console host details: OS name, "(emulated on <native architecture>)" after the process architecture when the bridge runs under Windows on Arm emulation or Rosetta 2, the Bun executable running the bridge, and a warning when the core binary is built for another platform.
- Web console: a SecurityAdmin can set the path of a tool that automatic detection misses (*Host & workers*, or `PUT`/`DELETE /api/system/tools/:name`; audited as `tool_path_configured` and `tool_path_cleared`). Only tools the bridge never runs can be set (`git`, `cargo`, `semgrep`, `osv-scanner`, `docker`; `codeql` no longer, since host analysis can run it, and a `codeql` path stored earlier is ignored). The path, the executable or the folder that contains it, must be absolute, exist and be able to run on the host; it is checked without running it, with a 2-second limit per file-system call and 5 seconds per check, on every save and once per tool search refresh (about every 60 seconds), and is used only for reporting (tool rows, topology reports). A path that later stops working, or whose drive does not answer in time, is reported as broken, and the row falls back to automatic detection. `SENTRA_GH_BIN` lets the host operator choose the `gh` the bridge runs. See web/README.md.
- Web console: `API_CONTRACT_VERSION` in `web/src/types/api.ts`, reported by the bridge as `apiContractVersion` in `/api/health` and `/api/system`. When the bridge runs code with a different contract (for example after Vite hot-reloaded the console but not the bridge), the console shows a banner asking to restart an older bridge, or, when the bridge is newer, to reload the page and in production to rebuild `web/dist` (`bun run build`), shows placeholders instead of failing on response shapes it does not expect, and renders each tab inside an error boundary.
- CI: the `web-test` job runs the web bridge unit tests (`bun run test` in `web/`) on `ubuntu-latest`, `windows-latest` and `macos-latest`.
- Web console: `GET /api/plugins` adds `directory`, `directorySource` (`environment`, `platform_default` or `none`), `directoryExists`, `diagnostics` (the core's discovery diagnostics passed through, plus the bridge's own `plugin_dir_*` and `plugin_entry_ignored` entries), `hasErrors` and `hint`, and the *Plugins* tab shows them. `pluginDir` is kept as a deprecated alias of `directory`. `API_CONTRACT_VERSION` is 4.

- `sentra codeql import --sarif <file> --workspace <dir> [--max-results <n>] [--json]`: normalizes CodeQL SARIF produced elsewhere (a local run, GitHub Actions) into the CodeQL result JSON (`schema_version`, `command`, `workspace`, `codeql_version`, `suite`, `pack_download_allowed`, `target_code_executed`, `languages`, `findings`, `results_total`, `results_outside_workspace`, `truncated`, `warnings`, `source_tool`). Each finding has `rule_id`, `rule_name`, `message`, `severity` (from `security-severity`: >= 9.0 critical, >= 7.0 high, >= 4.0 medium, > 0 low; otherwise from `problem.severity` or the SARIF level), `security_severity`, `problem_severity`, `precision`, `cwe`, `tags`, a workspace-relative `path`, lines and columns, `fingerprint` (`primaryLocationLineHash` joined to `primaryLocationStartColumnFingerprint` or the start column, else a SHA-256 of rule, path, line and message), `help_uri` and `language`; each `languages[]` entry lists the `rules` that ran. Rules are read from `tool.driver` and `tool.extensions`. SARIF over 64 MiB (`sarif_too_large`), invalid JSON (`sarif_invalid`) and runs of other tools (`sarif_not_codeql`) are rejected, and results whose path is absolute or leaves the workspace are dropped and counted.
- `sentra codeql analyze` (opt-in host analysis, [ADR-0011](docs/adr/0011-opt-in-host-codeql-analysis.md)): runs an operator-installed CodeQL CLI on the host and returns the same JSON. It refuses to start without `--accept-codeql-terms` (`codeql_terms_not_accepted`); `--codeql` must be the `codeql.exe` of a CodeQL distribution on Windows (never `codeql.cmd`) or its `codeql` launcher elsewhere (`codeql_not_found`); `--work-dir` and `--pack-cache` must be outside the workspace (`work_dir_inside_workspace`, `pack_cache_inside_workspace`). Only `codeql database create --build-mode=none` and `codeql database analyze` are used, for actions, cpp, javascript, python and ruby; go and swift (no build mode `none`) and rust, csharp and java (their build-mode `none` extractors run Cargo build scripts and procedural macros, `dotnet restore`, or the project's Gradle wrapper or Gradle/Maven) are reported as skipped with the reason. Query packs come from the distribution or `--pack-cache`, and `codeql pack download` runs only with `--allow-pack-download` (`codeql_query_pack_missing` when no language could run). Options: `--language` (repeatable), `--suite code-scanning|security-extended`, `--threads`, `--ram`, `--timeout-secs` (default 1800; `codeql_timeout`), `--max-results` (default 5000). A failing step's reason leaves out CodeQL's progress lines and root-installation warning, and starts with an explicit note when CodeQL's Java VM ran out of memory. Tested with a fake CodeQL launcher on Windows 11 x64 and, on 2026-11-11, with CodeQL CLI 2.27.4 on the same host (ADR-0011 experiment E3: a JavaScript fixture analyzed with 3 results and a Python fixture with 1, a Go file skipped; 34 s and 23 s with the query pack cached); Linux and macOS runs are pending.
- Web console: CodeQL ([ADR-0011](docs/adr/0011-opt-in-host-codeql-analysis.md)). *Settings → CodeQL* (`GET`/`PUT /api/settings/codeql`; audited as `codeql_settings_updated`) enables host analysis, off by default, only in a request that also accepts the CodeQL licence terms (`400 codeql_terms_required` otherwise), and sets pack download, suite, timeout (5–180 minutes, default 30), threads and RAM. When enabled, the scan's CodeQL stage runs `sentra codeql analyze` with a work directory under the bridge's temporary directory and the pack cache `<data dir>/codeql-packages`, at most one analysis bridge-wide (a second scan reports `analysis_busy`); otherwise the stage says why analysis did not run. *Findings → Import CodeQL SARIF* (`POST /api/tenants/:id/codeql/import`, up to 64 MiB on this route only; audited as `codeql_sarif_imported`) and *Findings → Sync GitHub code scanning* (`POST /api/tenants/:id/codeql/github-sync`, read-only GitHub REST, up to 1000 open CodeQL alerts; audited as `codeql_github_synced`) need `scan:run`. CodeQL findings have the source `codeql` and an origin (`host_analysis`, `sarif_import`, `github_code_scanning`) that is reconciled on its own; the findings filters, detail view, overview, executive report and SARIF export include them. `SENTRA_CODEQL_BIN` lets the host operator choose the launcher (checked at startup; `codeql.exe` with a PE header on Windows, the distribution's `codeql` launcher elsewhere). `API_CONTRACT_VERSION` became 5 (6 with the CodeQL progress and query pack changes below). Tested with a stubbed core and, on 2026-11-11 on Windows 11 x64, through the routes against the real core and CodeQL 2.27.4 (GitHub responses injected). See web/README.md.
- `sentra_core::plugin::run_contained`: runs a program to completion with a cleared environment, bounded output tails, a deadline and the plugin host's process-tree containment (Windows Job Object; Unix process group, plus marked processes and descendants on Linux and macOS).
- `sentra codeql analyze --progress [--heartbeat-secs <n>]`: progress events on stderr while the analysis runs, one JSON object per line, `{"progress": true, "event", "step", "language", "pack", "elapsed_ms", "duration_ms", "message"}`; `event` is `step_started`, `step_finished`, `step_failed`, `heartbeat` (every `--heartbeat-secs`, default 15, 1–3600, while a step runs) or `language_skipped`; `step` is `version`, `pack_download`, `database_create`, `database_analyze`, or `null` for `language_skipped`. The result on stdout and the error object, which stays the last stderr line and has no `progress` key, are unchanged, and without `--progress` nothing else is printed. `sentra_core::plugin::run_contained_observed` calls a callback while a contained program runs, which the heartbeat uses.
- `sentra codeql packs --codeql <launcher> --pack-cache <dir> [--language <id>]... [--suite code-scanning|security-extended] [--download] [--timeout-secs <n>] [--cancel-on-stdin-eof] [--progress] [--heartbeat-secs <n>] [--json]`: reports, per language, whether `codeql/<language>-queries` and the suite file are in the distribution's `qlpacks/` or the pack cache (`status` `present`, `missing`, `downloaded`, `failed` or `not_analysable`, with `version`, `source`, `location`, `suite_file`, `size_bytes`, `reason`) without running a program; with `--download` it fetches the missing packs of analysable languages one `codeql pack download` at a time (packs downloaded before a failure stay; each retried once) within `--timeout-secs` (default 1800) for all of them, with the launcher rules, environment allowlist, Windows path refusal, process-tree kill and `--cancel-on-stdin-eof` of `analyze`. A failed download returns `codeql_pack_download_failed` (exit 5) with CodeQL's message (control characters removed, bounded) and every language's state. CodeQL 2.27.4 unpacks a pack straight into its final directory in `--common-caches` (`PackageRegistry.installPackage`, `PackageArchive.unzipArchive`), so a download killed while unpacking would leave a partial pack that CodeQL takes as installed (once `qlpack.yml` exists) or refuses to download over ("not empty and is not a package"); each `codeql pack download` (in `packs` and in `analyze`) therefore writes into a new private staging directory `<pack cache>/.sentra-staging-*`, and only after exit code 0 are the complete pack versions renamed into `<pack cache>/packages/` (an unusable directory of the same version is replaced); the staging directory is deleted in every case. A download that the budget leaves no time for is reported as not started, not as killed. `--download` needs no `--accept-codeql-terms` (the query packs are MIT-licensed, [github/codeql `LICENSE`](https://github.com/github/codeql/blob/main/LICENSE); the downloaded packs carry no licence file of their own). Tested with a fake CodeQL launcher on Windows 11 x64 and, on 2026-11-11, with CodeQL CLI 2.27.4 on the same host (a listing of a copied pack cache: actions, javascript and python present, cpp and ruby missing; through the web console, a download of `codeql/ruby-queries` 1.7.0 in 4 min 22 s with a heartbeat every 15 s; through the staging directory, a download of `codeql/actions-queries` 0.6.39 in 3 min 47 s, and a download of `codeql/python-queries` cancelled after 40 s that left the pack cache empty).
- `sentra codeql analyze --download-timeout-secs <n>` (default 1800): pack downloads have their own budget and no longer use `--timeout-secs`.
- `sentra codeql analyze --typescript-runtime <path>`: the JavaScript runtime that CodeQL's JavaScript extractor parses TypeScript with, passed as `SEMMLE_TYPESCRIPT_NODE_RUNTIME` (an absolute local path of a native executable outside the workspace: a `.exe` with a PE header on Windows, an ELF or Mach-O file elsewhere; on Windows no `&`, `^`, `!` or `%`; otherwise `invalid_typescript_runtime`, exit 4). Without it the core uses the first `bun` on its `PATH` (absolute entries outside the workspace), else CodeQL's default (`node` on `PATH`) with a warning when javascript is analysed. No other `SEMMLE_*` or `LGTM_*` variable reaches CodeQL.
- `sentra codeql analyze --exclude <glob>` (repeatable, at most 50): relative globs (no `..` segment, no `:`, `/` as separator, no control characters, at most 200 characters; otherwise, and for a 51st glob, `invalid_exclude`, exit 4) that CodeQL's extractors leave out, passed as `LGTM_INDEX_FILTERS` `exclude:` lines (read by the javascript, python, ruby and actions extractors of CodeQL 2.27.4; the C/C++ build-mode-`none` driver honoured it on a two-file fixture). `--codescanning-config` is not used, because it makes CodeQL resolve query packs, which searches the directories next to the distribution (the whole drive for a distribution directly below `D:\`, 265 s observed). The CLI now accepts up to 160 arguments (was 64) to leave room for them.
- Web console (`API_CONTRACT_VERSION` 6): the scan stream has a `progress` event carrying each step of `sentra codeql analyze --progress` as a readable line ("Downloading query pack codeql/javascript-queries — first run only; …", "Still downloading … (2 min 15 s)", "Creating the javascript database (build mode none; TypeScript is parsed with Bun)", "javascript finished: 3 results in 34 s", skips with reasons), shown in the event log and on the CodeQL stage card with a first-run hint. *Settings → CodeQL → Query packs* lists the query packs per language (`GET /api/settings/codeql/packs`, `read`; `sentra codeql packs --json`, shared and reused for 30 s) and downloads the missing ones (`POST /api/settings/codeql/packs/download`, `settings:write`; JSON or Server-Sent Events with the scan stream's keep-alive; closing the stream cancels it; audited as `codeql_packs_downloaded`, refusals included). A download shares the bridge-wide one-CodeQL-operation lock with host analysis (`409 codeql_busy`; a scan started during a download reports `analysis_busy`), needs a launcher (`409 codeql_launcher_unavailable`) and, as a Sentra decision because it runs the CodeQL CLI on the host, host analysis enabled with accepted terms (`409 codeql_disabled`). New settings: `downloadTimeoutMinutes` (5–180, default 30; passed as `--download-timeout-secs` when pack download is allowed, and the budget of *Download missing packs*) and `excludePaths` (default `**/node_modules`, `**/target`, `**/dist`, `**/.git`; passed as `--exclude`; the 200-character limit counts UTF-16 code units, as the bridge passes them on). Without a RAM setting the bridge now always passes `--ram` = half of the host's available memory (the *Host* page's reading), kept between 1024 and 8192 MiB, and the stage message names the value and the rule (and says when the reading is only `os.freemem()` because `MemAvailable` or `vm_stat` could not be read; 2048 MiB only when even that fails); `ramAuto` in the settings view shows it. The bridge passes the Bun executable it runs on as `--typescript-runtime`, so no Node.js is needed, except when that Bun lies inside the scanned workspace (the core would refuse it): then it is not passed and the stage message says why; the isolation note in *Settings → CodeQL* says that no Node.js is needed only when the bridge can pass its Bun. The settings view's `running` names the operation (analysis or pack download) and who started a download. Stopping a scan explains that CodeQL and a download in progress stop, that finished packs stay in the cache and that the interrupted pack is discarded (downloaded again by a scan only if pack download is allowed). The bridge releases the CodeQL lock before it reads the listing a download returns, and after *Stop download* the panel waits (at most 30 s) until the bridge no longer reports the download as running. "first run only" is said only in a scan; a retry shows as "Retrying the download of … (attempt 2 of 2)". Tested with a stubbed core and, on 2026-11-11 on Windows 11 x64, in-process against a release build of the core and CodeQL 2.27.4 (see web/README.md, Query packs).
- ADR-0011 (Accepted 2026-11-11): opt-in host CodeQL analysis in build mode `none`, narrowly and partially superseding ADR-0004; ADR-0004 and the ADR index carry a pointer, and docs/LIMITATIONS.md section 9, docs/THREAT_MODEL.md and SECURITY.md describe the exception and its residual risks.

### Changed
- Web console rebuilt to show real data only. Removed all seeded findings, patches, sessions, audit entries, workers, advisories, trends and scores; fake pull requests and CI runs; simulated webhook dispatch; fake intel sync; canned AI patches that were always reported as verified; and the hard-coded coverage ledger and reconnaissance reports. Every view now reads the core CLI, read-only core stores, the bridge's persisted history, GitHub, OSV (opt-in) or configured model providers, and shows an explicit empty or "not configured" state otherwise.
- Web bridge (`web/server.ts`, `web/server/`) rewritten:
  - binds to loopback by default;
  - token authentication and server-side role permissions;
  - Host, Origin and CSRF guards; no CORS;
  - path confinement, an SSRF guard, encrypted credential storage, and an HMAC-chained append-only operator audit log;
  - webhook HMAC/token verification with duplicate-delivery detection;
  - a production mode that serves the built UI.
- The bridge no longer writes to core stores. Each workspace has its own core store under `<data dir>/core-stores/`.
- The patch engine applies hunks by position with exact context matching. It applies all hunks or none, and it reports `already_patched` only when every hunk's post-image is in place.
- `sentra tenant list` no longer seeds demo tenants.
- Skill installation writes on-demand `<skills dir>/<id>/SKILL.md` trees in each agent's documented location (`.agents/skills` for Zed, Warp, Codex, Windsurf, OpenHands, Goose and Kimi) and no longer appends playbooks to always-on rule files (`.cursorrules`, `.windsurfrules`, `.clinerules`, `.roorules`, `CONVENTIONS.md`, `copilot-instructions.md`); unmodified legacy blocks and files are removed after a backup. Cody is unsupported; Amazon Q, Continue and Replit are workspace-only; Aider gets `read:` entries in `.aider.conf.yml`. See docs/EXTENSIONS.md for the target table.
- MCP registration writes each agent's documented configuration file (for example `.mcp.json` and `~/.claude.json` for Claude Code, TOML for Codex, YAML for Goose, Hermes and Continue); the generic `.agents/mcp.json` fallback is gone. Aider, OpenHands, Replit and Cody fail with `mcp_unsupported_target`, and unsupported scopes with `unsupported_scope`.
- `install`, `install --mcp`, `skills`, `prompt` and `plugin` failures exit non-zero with specific error codes (for example `skill_not_found` 7, `mcp_config_unparseable` 4, `manual_config_edit_required` 6, `plugin_timeout` 5, `plugin_duplicate_id` 4); `install --json` output is built with serde_json and is valid JSON on Windows. `install --json` `count` is the number of skills; `file_count` and `file_changes` list the files.
- `sentra skills list --json` returns `{schema_version, command, count, skills}` instead of a bare array; `skills show --json` adds `schema_version`, `command` and `files`.
- `sentra prompt --skills` appends the playbooks to the workflow prompt, keeping its grounding rules and `expected_schema`, removes duplicate ids and rejects unknown ids (`skill_not_found`). The MCP `sentra_generate_prompt` tool does the same.
- The MCP server negotiates the legacy revisions `2025-11-25`, `2025-06-18`, `2025-03-26` and `2024-11-05` instead of always answering `2026-07-28`, which it does not implement. The stdio loop enforces the 1 MiB line quota while reading; oversized lines and invalid UTF-8 are answered with JSON-RPC errors and no longer stop the server.
- `sentra plugin` loads adapters only from `--dir` or the default plugin directory (`SENTRA_PLUGIN_DIR`, else the platform configuration directory), never from the working directory, its parents or `examples/adapters`; `plugin run --workspace` is passed to the adapter.
- Web console API: `HostInfo.freeMemoryBytes` is replaced by `availableMemoryBytes` with a `memorySource`; `ToolAvailability` adds `resolvedPath`, `resolvedVia`, `source` (`configured` and `environment` included), `onProcessPath`, `binary`, `usage`, `usageNote`, `shadowed`, `selection`, `configuredPath`, `configuredPathProblem`, `pathConfigurable` and `pathHint`; `SystemStatus` adds `apiContractVersion`, `toolSearch` and `core.binary`. These changes are `API_CONTRACT_VERSION` 3 (the plugin directory fields above raise it to 4). Tool rows of topology reports stored by earlier bridges are upgraded when read.
- Web console: the scan's CodeQL stage message and the topology report note name the locations searched for tools instead of "on PATH", and say when the persisted PATH could not be read.
- `sentra sync-advisories --json` reports `source_kind`, `advisory_entries_parsed` (one entry per affected package), `files_parsed`, `files_skipped` and `persisted: false` instead of `advisories_ingested` and `status`; the text output says nothing was persisted. `--database` is no longer accepted and silently ignored: it fails with `not_implemented` (exit 5), because the store has no advisory table.
- `sentra propose-pr` output says what it is: JSON adds `local_preview_only: true`, `pull_requests_created: false`, `patch_diffs_illustrative: true`, `advisory_db_source`, `advisory_db_records` and `advisory_db_updated_at`, and the text output labels branches and `gh` commands as suggested, not created or run. `LocalWorkspace::propose_remediations` and `RemediationPrPackage::from_advisory_match` take a description of the advisory source, which the preview body quotes.
- `sentra audit --json` adds `lockfiles_audited`, `lockfiles_unparsed` and a `lockfile` per finding, and is built with serde_json (keys in alphabetical order); the text output lists the audited and unparsed lockfiles. `LocalAuditReport` adds `lockfiles`, `unparsed_lockfiles` and `match_lockfiles`.
- `MultiUserSecurityAudit::run_assessment` reports a gate as passed only when it was evaluated: an empty registry or a fleet without a leasable worker leaves gates 2 and 3 not assessed, and gates 4 (secret inheritance) and 5 (audit-trail tamper evidence), which have no implemented check, are always reported as not assessed, so the result is currently always `Blocked`.
- `ingest_osv_directory_report` (with `OsvDirectoryIngest`) reports how many top-level `.json` files of an OSV directory were parsed and skipped; `ingest_osv_directory` still returns the entry count.
- Web console: when `SENTRA_PLUGIN_DIR` is unset, the bridge uses the core's platform default plugin directory as reported by `sentra plugin list --json`, where plugins used to be disabled. It refuses a default that is not an absolute path (on Windows: a drive-letter path whose real path, with links, junctions and mapped drives resolved as far as the host's `realpath` reports them, is not a UNC or device path) or that overlaps the bridge data or temporary directories, the system temporary directory, the repository or a registered workspace; network mounts on macOS and Linux are not detected. On Windows, `APPDATA` is not handed to the core when it, or the real path of `<APPDATA>\sentra\plugins`, is a UNC or device path, and the core is not asked while that check does not answer. Real-path and existence checks are asynchronous with a 2-second deadline. Only the variables the core reads on the bridge's platform are passed to it and checked. It never creates the directory, and a directory created later is listed without a restart. The *Plugins* tab, probe, run and the console's `plugins` command use the same directory and answer `412` only when no plugin directory is in use. See web/README.md.
- Web console: *Rediscover* on the *Plugins* tab requests `GET /api/plugins?refresh=1`, which lists again instead of reusing a listing from the last 15 seconds, and probe and run do the same before they start an adapter (a listing still running is joined). `SentraCli.runShared` takes `fresh`.
- `sentra codeql --sarif` and the MCP `sentra_codeql_ingest` tool report `candidate_findings_parsed` instead of `findings_admitted`, and the CLI JSON adds `findings_stored: false`; the text output says "Candidate findings parsed (not stored)". Nothing was admitted as evidence or stored.
- Semgrep example adapter (2.0.0) runs local rules only: `--args '{"config": "<path inside the workspace>"}'` or a `rules/` directory the operator adds next to the adapter. Registry rulesets (`p/`, `r/`, `s/`), `auto` and URLs are refused to match its declared `strictly_denied` egress policy; its former default, `p/security-audit`, was downloaded from the Semgrep registry. It passes `--metrics=off`, `--disable-version-check` and, unless `git_ignore` is true, `--no-git-ignore`. It no longer declares the unimplemented `source_discovery` capability, and it rejects unknown arguments, such as the `rule_suite` key the docs/PLUGINS_GUIDE.md example used to pass.

### Fixed
- `sentra codeql analyze --allow-pack-download` gave no sign of life while it downloaded query packs: on 2026-11-11 a scan of the Sentra repository from the web console showed only the command line, because `codeql pack download` ran for javascript, python and actions in turn before any analysis (about five minutes per pack at about 130 KB/s on the development host) and CodeQL prints nothing meanwhile; the operator cancelled after about 15 seconds. With `--progress` every step, skip and download is reported as it happens, with a heartbeat while a step runs, and `sentra codeql packs --download` fetches the packs ahead of a scan. `--timeout-secs` now covers `codeql version`, `database create` and `database analyze` only; downloads use `--download-timeout-secs`, a download that runs out of it fails its language while languages with packs are still analyzed, and a failed download is retried once.
- Host CodeQL analysis of a workspace with TypeScript files failed on a host without Node.js: on 2026-11-11 a scan of the Sentra repository ended with "codeql database create exited with code 2" for javascript after 340 s (CodeQL: "Could not start Node.js. It is required for TypeScript extraction."). The web console now passes its own Bun as the TypeScript runtime, and the core falls back to `bun` on its `PATH`; with Bun 1.4.4 the repository's javascript database was built in 32 s.
- Host CodeQL analysis extracted build and dependency output (rustdoc HTML under `target/doc`, the built `web/dist` of the Sentra repository); the web console's default `excludePaths` now leaves `node_modules`, `target`, `dist` and `.git` out (348 files extracted for the repository, none of them below `target/` or `web/dist`).

### Security
- `sentra codeql analyze` on Windows refuses a workspace, `--work-dir` or `--pack-cache` path containing `&`, `^`, `!` or `%` (`invalid_workspace`, `unsafe_directory`), and a CodeQL distribution path containing one (`codeql_not_found`), before CodeQL starts. CodeQL's Windows extractor scripts expand the source root unquoted (`set LGTM_SRC=%CD%`), so a workspace below a directory such as `R&D` made `cmd.exe` run part of the path, or a file in the workspace, as a command, which broke `target_code_executed: false`.
- `sentra codeql analyze` on Linux and macOS creates the run directory new (never reused) with mode 0700, creates missing `--work-dir`/`--pack-cache` directories with mode 0700, and refuses an existing work directory or pack cache that another user owns or that group or others can write (`unsafe_directory`). Through a shared work directory such as `/tmp/sentra-codeql`, another local user could swap the run directory, whose redirected `HOME` the extractors' host Python reads `.pth` files from, or the SARIF. The README example now uses `~/.cache/sentra-codeql`.
- `sentra codeql analyze --cancel-on-stdin-eof` cancels the analysis and kills CodeQL's process tree when standard input reaches end of file (`codeql_cancelled`). The web bridge uses it: cancelling a scan closes the core's stdin and waits for the core to stop CodeQL (killing the core only after 30 seconds), so on Linux and macOS the one-analysis lock is no longer released while CodeQL keeps running in its own process group. The CLI binary no longer locks stdin for its whole run.
- Documentation: ADR-0004's supersession note and docs/THREAT_MODEL.md said host CodeQL analysis needs an administrator; the core CLI runs it for anyone who passes `--accept-codeql-terms`, which acknowledges the licence and authorises nothing. ADR-0011 now says so, says that the GitHub sync maps alerts in the bridge rather than through the import contract, and gives the `codeql version` output bound (256 KiB).
- `sentra codeql analyze` never passes tokens, provider keys, `SENTRA_*`, `CODEQL_*` or `JAVA_TOOL_OPTIONS` to CodeQL: only `PATH` (without relative entries or entries inside the workspace), `PATHEXT`, `SystemRoot`, `SystemDrive`, `windir`, `ComSpec`, `PROCESSOR_ARCHITECTURE`, `NUMBER_OF_PROCESSORS`, `LANG` and `LC_ALL` are copied, and `TEMP`, `TMP`, `TMPDIR` and `HOME` (on Windows also `USERPROFILE`, `APPDATA`, `LOCALAPPDATA`) point into a per-run directory that is deleted afterwards. It sets `NoDefaultCurrentDirectoryInExePath=1` on Windows, because CodeQL starts its extractor scripts in the source root and Windows otherwise runs a program of that name from the current directory (verified 2026-11-11 for CreateProcess and `cmd.exe` on Windows 11), and `CODEQL_EXTRACTOR_PYTHON_ENABLE_SITE=1`, which skips the Python extractor's `python -S -c "import gzip"` probe that would import a `gzip.py` from the source root, and `PYTHONDONTWRITEBYTECODE=1`, so the host Python started by the Python extractor does not write a `__pycache__` into the CodeQL distribution (observed with CodeQL 2.27.4 and Python 3.14 on 2026-11-11 before the variable was set).
- Fixed the legacy bridge's critical issues: unauthenticated API reachable from any interface or website, arbitrary file read and write, plugin command execution through client-supplied manifest paths, stored provider keys forwarded to client-chosen endpoints, and client-supplied roles.
- `sentra install --mcp` no longer replaces configuration files it cannot parse (JSONC, BOM, UTF-16, unexpected structure): such files are left untouched and the command prints the snippet to add by hand. Every edit keeps unrelated content, writes `<file>.bak` first and replaces the file atomically.
- Removed the `sentra_install_skills` MCP tool, which let a model write files anywhere without approval, and the no-op `sentra_apply_checkout_mutation`. MCP tools no longer return fabricated workspace, session or findings data, and file paths are confined to the launch workspace.
- Web console: `gh auth token` was started with the bridge's full environment (including `SENTRA_WEB_SECRET_KEY`, `SENTRA_WEB_TOKENS` and the webhook secrets), without a timeout, from whatever `Bun.which("gh")` returned, which on Windows includes `.cmd`/`.bat` wrappers and which searches relative `PATH` entries. It now runs with an allow-listed environment and a 5-second timeout, only from `SENTRA_GH_BIN` (checked at startup: an existing native executable, not a script), the process PATH or the persisted PATH (never from standard install locations, which on Windows include directories any local user can create, and never from a path set in the web console), on Windows only as a `.exe` or `.com`, and on macOS and Linux a persisted-PATH match only when it, its target and their directories are owned by root or the bridge user and writable neither by others nor by a non-root group. The page names the file that is run, or why a match was skipped.
- Web console: the `sentra` binary fallback on `PATH` skips relative and UNC entries and, on Windows, accepts only `sentra.exe`/`sentra.com`, where `Bun.which("sentra")` also matched batch wrappers and relative entries. Standard install locations are never used for it.
- Web console: a tool path entered in the console never becomes a program the bridge runs. Only tools the bridge never runs can be set (`gh`, `bun` and, since CodeQL host analysis can run it, `codeql` are refused with `409`), and the code paths that start programs (the `gh` lookup, the `sentra` binary resolution) never read the stored paths. Validation only reads the file system: it refuses relative, UNC, device and drive-relative paths before touching them, expands no environment variables (only a leading `~` on macOS and Linux), and reads at most 64 KiB of the file header.
- Web console: host detection never executes a discovered tool, nor a path set in the console. It starts only fixed system programs, by absolute path, without a shell, with a minimal environment and a time limit: on Windows `powershell.exe -NoProfile -NonInteractive -NoLogo -Command -` with a fixed registry script on standard input (no `-EncodedCommand`, no `-ExecutionPolicy` override), limited to 15 seconds; the script uses only .NET calls (no cmdlet) and PowerShell gets a `PSModulePath` restricted to its own modules, because auto-loading a module for `ConvertTo-Json` or `New-Object` on a host with many modules and an empty module analysis cache took more than 15 seconds on GitHub's Windows runners; whose result is reused for 10 minutes and, after a failure, retried after 1, 2, 4 and 8 minutes and then at most every 10 minutes; on macOS `sw_vers`, `sysctl` and `vm_stat`, limited to 5 seconds each. On Linux everything is read from files. UNC and device paths are never listed, whether they come from a `PATH` entry or from an install-location variable such as an `APPDATA` redirected to a share, and search refreshes check and list directories asynchronously with a 2-second deadline each.
- `sentra propose-pr`: the suggested `gh pr create` command inlined the Markdown body and the lockfile version inside double quotes, so pasting it into a shell expanded backticks and `$(...)`, including text from the scanned repository's lockfile (a version such as `4.17.11-$(whoami)` reached the command). The command now reads the body from `<proposal_id>.md` (`--body-file`) and replaces every character a POSIX shell, PowerShell or `cmd.exe` could interpret in its title and branch with `_`; the `title` field keeps the raw text.
- Plugin host: a planted `manifest.json` in a repository can no longer shadow an operator adapter. Adapters run with an allowlisted environment, enforced time and output quotas and drained stderr, and are killed with their process tree on every exit path. A program path containing a separator is resolved inside the adapter directory and must stay inside it; a bare name (such as `python` or `bun`) is looked up in the absolute `PATH` entries, and an absolute program path is used as given. Memory and egress limits remain declared, not enforced.
