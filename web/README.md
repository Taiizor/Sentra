# Sentra web console

The web console is an operator UI for the Sentra core. It has two parts:

- **Bridge** (`server.ts`, `server/`): a Bun HTTP server that authenticates operators, enforces
  role permissions, runs the `sentra` CLI, reads core stores read-only, and talks to GitHub, OSV
  and configured model providers.
- **UI** (`src/`): a React 19 + Vite single-page app that renders only what the bridge returns.

Every value in the UI comes from a real source, listed below. When a source is missing or not
configured, the UI shows that state and does not substitute sample data.

## Data sources

| Area | Source |
| --- | --- |
| Workspaces (tenants) | Bridge registry in `sentra-web.db`, created by a SecurityAdmin. Each workspace gets its own core store, initialised with `sentra init`. |
| Session state, tasks, core audit events, budget | The workspace's core store. Session state comes from `sentra status`; tables the CLI does not expose are read through a read-only SQLite connection. |
| SAST findings | `sentra scan --workspace <ws> --database <store> --json`. Results are persisted and reconciled by the bridge, because the core does not persist findings. |
| Dependency vulnerabilities | Package inventory from `sentra inventory` (the core's lockfile parsers), matched against [OSV.dev](https://osv.dev). OSV access is **opt-in**: see *Privacy* below. |
| Language probe | `sentra codeql --workspace <ws> --json`. Language counts are by file extension; the CodeQL commands it prints are suggestions and are not executed. |
| CodeQL findings | Three origins, each reconciled on its own: CodeQL host analysis (`sentra codeql analyze`, build mode none, **off by default**), an imported CodeQL SARIF file (`sentra codeql import`), and open GitHub code scanning alerts of tool CodeQL for the workspace's repository. See [CodeQL](#codeql). |
| Trends and overview | Computed from the persisted scan runs and finding history. The risk score is shown with its formula. |
| Patches | Candidates generated by a configured model provider from a real source excerpt, then dry-run against the workspace by the core patch engine. **No patch is ever reported as verified.** |
| Pull requests and CI runs | GitHub GraphQL/REST, using the `gh` CLI session, `GITHUB_TOKEN`/`GH_TOKEN`, or a token stored by an admin. |
| PR security scans | The PR's changed files at the head commit, fetched from GitHub into a private temp directory and scanned with `sentra scan`. |
| Webhook deliveries | Persisted only after HMAC (GitHub) or token (GitLab) verification. |
| Operator audit log | Append-only chain in `sentra-web.db`. Each entry is HMAC-SHA256 linked to the previous one and can be verified from the Audit tab. |
| Host information | The bridge host's real OS metrics and tool locations, read from the OS and from files (see *Host and tool detection*). The core has no remote-worker registry, and the UI says so. |

## Requirements

- [Bun](https://bun.sh) — the only JavaScript runtime and package manager used by Sentra.
- The `sentra` core binary. Build it from the repository root:

  ```bash
  cargo build --release -p sentra-cli
  ```

  The bridge looks for the binary in this order:
  1. `SENTRA_BIN`
  2. `target/release/sentra[.exe]`
  3. `target/debug/sentra[.exe]`
  4. `sentra` on the bridge process `PATH` (on Windows only `sentra.exe`/`.com`, never a batch wrapper). Standard install locations such as `~/.cargo/bin` are not used for the binary, because it is executed; see [Host and tool detection](#host-and-tool-detection).

## Running

### Development

```bash
cd web
bun install
bun run dev        # bridge on 127.0.0.1:3001, Vite on http://localhost:5173
```

On first start the bridge creates a loopback-only admin token, unless `SENTRA_WEB_TOKENS` is set. It prints a sign-in URL like this:

```
[sentra-web] No SENTRA_WEB_TOKENS configured: a loopback-only admin token is in use.
  token file : <data dir>/web-admin.token
  sign in    : http://localhost:5173/#token=<token>
```

The token is carried in the URL fragment, which browsers never send to the server. The UI exchanges it for an `HttpOnly`, `SameSite=Strict` session cookie and then removes it from the address bar.

### Production

```bash
cd web
bun install --frozen-lockfile
bun run build      # type-checks UI + bridge, builds web/dist
bun run start      # serves web/dist and /api from one origin (default 127.0.0.1:3001)
```

To reach the console from other machines, put it behind a TLS-terminating reverse proxy. You must also:

- configure role tokens (`SENTRA_WEB_TOKENS`),
- set `SENTRA_WEB_HOST`, `SENTRA_WEB_ALLOWED_ORIGINS` and `SENTRA_WEB_COOKIE_SECURE=true`,
- set `SENTRA_WEB_TRUST_PROXY=true` only when the proxy sets `X-Forwarded-For`.

If you bind a non-loopback address without tokens, the bridge refuses to start.

## Roles

Roles come only from the authenticated credential. They are never read from the URL, local storage or request bodies.

| Permission | Viewer | Operator | SecurityAdmin |
| --- | :---: | :---: | :---: |
| Read dashboards, findings, audit logs, PRs | ✓ | ✓ | ✓ |
| Verify the audit chain | ✓ | ✓ | ✓ |
| Run scans, triage findings, query OSV, generate patch candidates and prompts, probe plugins, run console commands, scan PRs, edit the coverage ledger, import CodeQL SARIF, sync GitHub code scanning alerts | | ✓ | ✓ |
| Apply/roll back patches, run plugins, create draft PRs, post PR comments, set commit statuses, test providers, register workspaces, change settings (including enabling CodeQL host analysis) | | | ✓ |

Creating a pull request (publication) and posting a comment or commit status (disclosure) are separate permissions. The UI asks for confirmation before every outward-facing or destructive action.

## Security model

- **Network:** binds to loopback by default. A `Host` allowlist blocks DNS rebinding. No CORS headers are sent, and in production the UI is served from the same origin.
- **Authentication:** bearer tokens for API clients, or an `HttpOnly`, `SameSite=Strict` session cookie for the UI. Login attempts are rate-limited.
- **CSRF:** state-changing cookie requests must carry an allowed `Origin` (or `Sec-Fetch-Site: same-origin`) and the `X-Sentra-Client: console` header. JSON bodies require `Content-Type: application/json`.
- **Paths:** clients never send filesystem paths for workspaces, stores, backups or manifests. File reads are confined (after symlinks are resolved) to the registered workspace. Secret files and the data directory are denied, and lines with open secret findings are redacted. A SecurityAdmin can set the path of a tool the bridge never runs; the bridge only checks that file and never runs it (see [Tool paths set in the console](#tool-paths-set-in-the-console)).
- **Process execution:** the core runs without a shell, from the data directory, with a minimal environment, a timeout, an output cap and a concurrency limit. Credentials are never passed to the core or to plugin adapters. Through the core, CodeQL runs on the bridge host only while an admin has enabled host analysis (see [CodeQL](#codeql)).
- **Outbound requests:** model provider endpoints are fixed. The only custom endpoints allowed are explicitly loopback ones (local runtimes) or public HTTPS hosts that pass a private-address and metadata-address guard. Responses are size- and time-limited.
- **Secrets at rest:** provider API keys and the GitHub token are encrypted with AES-256-GCM. The key comes from `SENTRA_WEB_SECRET_KEY` or `web-secret.key`.
- **Audit:** every state-changing action is appended to the HMAC-linked operator audit chain, with success, failure or denial recorded. This includes requests rejected by the Origin, CSRF or validation checks. SQLite triggers reject `UPDATE` and `DELETE`. Verification detects:
  - edited, reordered or removed entries, because they break the chain;
  - removal of the newest entries, through a MAC-protected head checkpoint stored in the same database.

  An attacker who can write the database and also roll back that checkpoint, or who holds the secret key, can hide truncation. For a stronger anchor, record the reported head hash somewhere off this host.
- **Webhooks:** the bridge verifies the HMAC or token over the raw body before parsing it. Duplicate deliveries are ignored. Unauthenticated requests are counted but never stored.

  Each endpoint answers `503` until its secret or token is configured. GitHub and GitLab cannot reach a loopback bind, so expose the bridge through an HTTPS reverse proxy or tunnel and add that public host to `SENTRA_WEB_ALLOWED_HOSTS`: the Host check runs before any route, webhook routes included.

## API-only routes

Some routes have no console screen. Call them with a bearer token, for example `curl -H "Authorization: Bearer <token>"`:

- `POST /api/tenants/:id/prompts`: renders a core AppSec prompt for the workspace.
- `GET /api/skills` and `GET /api/skills/:id`: the embedded skill catalogue.
- `POST /api/tenants/:id/diff`: compares two directories inside registered workspaces.
- `PUT /api/tenants/:id`: renames a workspace or sets its GitHub repository.
- `POST /api/tenants/:id/scans` without `Accept: text/event-stream`: runs to completion and returns the run.

Workspaces are unregistered under *Settings → Workspaces*. Unregistering keeps the core store and history on disk.

PR scans and the Pull requests view need a GitHub credential: the `gh` CLI session, `GITHUB_TOKEN`/`GH_TOKEN`, or a token stored by an admin. They also need the `sentra` binary.

## Privacy

- **OSV.** Dependency vulnerability lookups send package names and versions (never source code) to `https://api.osv.dev`. They are disabled until a SecurityAdmin enables them under *Settings → Threat intelligence*.
- **Model providers.** Patch generation sends one source excerpt (±60 lines around the finding) to the provider you select. Secret-leak findings are never sent to a provider.
- **CodeQL.** Host analysis runs locally. It contacts GitHub's container registry (ghcr.io) only when an admin allows query pack download. *Sync GitHub code scanning* reads alerts from the GitHub API with the GitHub credential and writes nothing to GitHub. An imported SARIF file is stored only as a temporary file that is deleted after parsing.

### Upgrading from the earlier dashboard

On first start, the bridge reads the earlier store `<data dir>/sentra.db` in read-only mode and imports workspace registrations whose directories exist. It skips the demo rows `tenant-alpha` and `acme-corp`. Nothing else is imported, and the legacy file is never modified.

That file contains `tenants` and `system_settings` tables that the earlier bridge added. These tables make every core command on that store fail its schema check, which is why each workspace now uses a fresh store under `core-stores/`. Once you have checked the import, you can delete the legacy `sentra.db*` and `ws_*.db*` files.

## Host and tool detection

*Host & workers* and *Settings → System* describe the machine that runs the bridge. Tools are found automatically; the search has rules for Windows, macOS and Linux hosts, including Arm hosts and emulated processes (what has been tested on which host is listed at the end of this section). When detection misses a tool, a SecurityAdmin can set its path on *Host & workers* (see [Tool paths set in the console](#tool-paths-set-in-the-console)). Detection never runs a tool it finds, and a path set in the console is never run either. The only programs the bridge starts for detection are fixed system programs, called by absolute path without a shell, with a minimal environment and a time limit (15 seconds for the Windows registry read, 5 seconds for each macOS program); their results are cached:

| Host OS | Programs | Used for |
| --- | --- | --- |
| Windows | `%SystemRoot%\System32\WindowsPowerShell\v1.0\powershell.exe` | One registry read: the persisted system and user `Path` and the hardware `PROCESSOR_ARCHITECTURE`. |
| macOS | `/usr/bin/sw_vers`, `/usr/sbin/sysctl`, `/usr/bin/vm_stat` | OS name and version, Rosetta 2 / Apple silicon detection, available memory. |
| Linux | none | Everything is read from files. |

Everything else is read from files, with bounded reads.

On Windows, PowerShell is started as `powershell.exe -NoProfile -NonInteractive -NoLogo -Command -`, and the fixed, single-line registry script is written to its standard input. The command line carries no `-EncodedCommand` payload and no `-ExecutionPolicy` override, which endpoint security products commonly flag. A successful registry read is reused for 10 minutes. A failed one (PowerShell exits non-zero, does not answer within 15 seconds, prints output that cannot be parsed, or cannot be started, for example because Constrained Language Mode under WDAC or AppLocker blocks the script) is reused too: PowerShell is started again after 1, 2, 4 and 8 minutes, then at most once every 10 minutes, and the page shows when the next attempt is due. Directory contents are listed again every 60 seconds.

The 15-second limit allows for the slow start of Windows PowerShell 5.1, which loads the .NET Framework first: on a cold or busy host this takes several seconds (on GitHub's Windows runners, more than 5). The read starts in the background when the bridge starts. A request that needs the tool search or the native architecture before the first read has finished, such as the first load of *Host & workers*, waits for it, for at most 15 seconds; later requests use the cached result. A host where PowerShell takes longer than that on every attempt reports the persisted PATH as not read, and the native architecture is then taken from the bridge's environment (`PROCESSOR_ARCHITEW6432`, `PROCESSOR_ARCHITECTURE`), which reports AMD64 for an x64 process emulated on Arm.

### Why the bridge's own PATH is not enough

A process copies `PATH` when it starts. A directory added to `PATH` after the bridge (or the terminal that launched it) started, for example by an installer, is not on the bridge's `PATH`, so tools in it are invisible to the bridge's own lookups. A tool installed later into a directory that was already on its `PATH` (such as `~\scoop\shims`, `~/.cargo/bin` or `/opt/homebrew/bin`) is found. Services also start with a reduced `PATH`:

- macOS: `/etc/paths` and `/etc/paths.d` are applied by `path_helper` in login shells only. Processes started by launchd (LaunchAgents and LaunchDaemons, apps opened from the Dock or Finder, and what they start) get launchd's minimal `PATH`, and shell profiles (`~/.zprofile`, `~/.zshrc`), where `brew shellenv` usually adds `/opt/homebrew/bin`, are not read either.
- Linux: `/etc/environment` is applied by `pam_env` at login. systemd services, cron jobs and containers do not read it, nor shell profiles (`~/.profile`, `~/.bashrc`) that add `~/.local/bin`, `~/.cargo/bin` or `/home/linuxbrew/.linuxbrew/bin`.

### Search order

Each tool is looked up in these directories, in order. Empty, relative and duplicate entries are dropped. On Windows, UNC (`\\server\share`) and device (`\\?\`, `\\.\`) entries are skipped on purpose, because listing a share would make the bridge authenticate to that host on every refresh; the page shows how many were skipped. Standard install locations under such a path are dropped as well, before anything is listed, for example the Python directories under an `APPDATA` that Folder Redirection points to a share. The first match is reported, and up to four later matches are listed as shadowed. When a path was set for the tool in the console, or `SENTRA_GH_BIN` is set for `gh`, the search still runs, but the row reports that path; what the search found, its first match included, is then listed as other copies found by automatic detection (and is what the row falls back to when a console path stops working). The same file reached through another directory (for example `/bin` and `/usr/bin` on merged-`/usr` Linux distributions, or a symlinked directory) is reported once. A row shows a resolved target only when the path or one of its directories is a symlink or junction; a path that differs from its canonical form only through a Windows 8.3 short name (`C:\PROGRA~1`), a `subst` or mapped drive, or letter case is shown as it is.

Directories are checked and listed asynchronously when the search is refreshed, each with a 2-second deadline; a directory that does not answer in time is treated as empty (a standard install location as missing) until the next refresh.

1. **Process PATH** — the bridge's own environment; this is what its subprocesses inherit.
2. **Persisted system PATH**
   - Windows: `HKLM\SYSTEM\CurrentControlSet\Control\Session Manager\Environment\Path`. `%VAR%` references in these `REG_EXPAND_SZ` values are expanded from the bridge's environment; an entry that names a variable the bridge does not know (for example one created after it started) is skipped.
   - macOS: `/etc/paths`, then the files in `/etc/paths.d/`. If one of these files cannot be read, the entries that were read are still searched, and the page reports a partial read.
   - Linux: the `PATH=` line of `/etc/environment`.
3. **Persisted user PATH** — Windows: `HKCU\Environment\Path`. macOS and Linux have no persisted user PATH.
4. **Standard install locations** — per-OS directories that package managers and installers use, such as `~/.bun/bin`, `~/.cargo/bin`, `/opt/homebrew/bin`, `/usr/local/bin`, `~/.local/bin`, `/snap/bin` and `/home/linuxbrew/.linuxbrew/bin`. On Windows, Chocolatey's `bin` directory is included only when `ChocolateyInstall` is set; there is no `%ProgramData%\chocolatey` fallback, because any local user can create that directory.

Each match records its source and whether it is on the process PATH. If the persisted PATH could not be read, the page and scan messages say so and name only the locations that were searched.

When a tool is found only through steps 2–4, the page explains why the bridge cannot see it and what to change, depending on where it was found and on the host OS. The running Bun is left out of this notice: starting the bridge by absolute path from a directory that is not on `PATH` is normal. So are tools whose path was set in the console (even when that path is broken) or through `SENTRA_GH_BIN`: their rows say where the path came from.

| Found in | Windows | macOS | Linux |
| --- | --- | --- | --- |
| Persisted PATH (steps 2–3) | The bridge, or the terminal or application it was started from, predates the `PATH` change. Restart the bridge from a terminal opened from the Start menu or Explorer. A terminal inside an application that was already running (for example VS Code) inherits that application's old `PATH`, so restart the application first. A bridge run as a Windows service gets `PATH` changes only after a reboot, unless its service configuration sets `PATH`. | launchd did not apply `/etc/paths(.d)`, or the shell was opened before the change. Start the bridge from a new login shell, or set `PATH` under `EnvironmentVariables` in its launchd plist. | systemd, cron or a container did not apply `/etc/environment`, or the session predates the change. Set `Environment=PATH=…` in the systemd unit, or start the bridge from a new login shell. |
| Standard install location only (step 4) | The installer did not add the directory to any `PATH`. Add it to the user or system `Path` if other programs need it, then restart as above. | The directory is usually added by a shell profile (`~/.zprofile`) that launchd never reads. Start the bridge from a login shell, or add the directory in the launchd plist or `/etc/paths.d`. | The directory is usually added by a shell profile (`~/.profile`, `~/.bashrc`) that systemd and cron never read. Start the bridge from a login shell, or set `Environment=PATH=…` in its unit. `/snap/bin` is the exception: snapd adds it for login shells (`/etc/profile.d/apps-bin-path.sh`) and, through its systemd environment generator, for systemd services, so it is missing from cron jobs, containers, units that set their own `PATH` and sessions started before snapd was installed. |

The second row assumes the persisted PATH was read. If it could not be read, or was only partly read, the page does not claim that no `PATH` lists the directory: it says that this is unknown and gives both the restart advice and how to add the directory.

#### Package-manager shims (Windows)

- **Scoop** puts a copy of its generic `shim.exe` in `~\scoop\shims` for every command (for example `bun.exe`), next to a `bun.shim` text file whose `path = "…"` line names the real executable, usually under `~\scoop\apps\<app>\current` (not on `PATH`, so not searched). When a located `<name>.exe` has such a sibling `.shim` file, the row shows the shim's path with the target as its resolved path ("Scoop shim"), the [platform check](#platform-check) reads the target, and the Bun runtime is matched against the target. The `.shim` file is read with a size limit; only an absolute drive path is accepted as its target, and the target is never run by detection.
- **Chocolatey** shims in `%ChocolateyInstall%\bin` are generated by shimgen and carry their target inside the executable. They are not resolved: the row reports the shim itself, and the platform check reads the shim, not its target.

#### Which file is run

Finding a tool and running it are separate decisions. Standard install locations are searched only to report what is installed: some can be created by any local user, and on macOS and Linux they may belong to a different user than the one running the bridge. Paths set in the console are used only for reporting, too. The bridge itself runs only two programs found this way, and hands a third to the core:

- **`gh`** (`gh auth token`): the file `SENTRA_GH_BIN` names, when the host operator sets it (see [Configuration](#configuration)); no other `gh` is then run. Otherwise taken from the process PATH or the persisted PATH, never from a standard install location or a path set in the console. On Windows only a `.exe` or `.com` is started, never a `.cmd`/`.bat` (those run through `cmd.exe`); a script earlier in the search order is skipped in favour of a later `gh.exe`. On macOS and Linux, a match from the persisted PATH is run only if the directory it was found in, the file it resolves to and that file's directory are each owned by root or the bridge user and writable neither by others nor by a group other than root. A match that fails is skipped, and the *gh* row's usage note gives the reason, which names the path and one of:
  - "owned by uid N, which is neither root nor the bridge user (uid M)";
  - "writable by others";
  - "writable by group admin (gid 80), which is not root" (the group name comes from `/etc/group` when it is listed there). This is the case for Homebrew's `/opt/homebrew/bin` and, on Intel Macs, `/usr/local/bin`, which are group-writable by the `admin` group: any admin could replace the file. Such a `gh` is run only when its directory is on the bridge's process PATH.

  Process-PATH matches are not checked (the operator chose that `PATH`). On Windows, directory ACLs are not checked (reading them would mean starting another program); the persisted PATH is trusted as much as the process PATH, which Windows builds from it. `gh` runs with an allow-listed environment that excludes the bridge's secrets (`SENTRA_WEB_SECRET_KEY`, `SENTRA_WEB_TOKENS`, webhook secrets), and is stopped after 5 seconds. The *gh* row's usage note names the file that is run, or why none is.
- **`sentra`**: see [the binary lookup order](#requirements); only the process PATH is used, not the persisted PATH, standard install locations or paths set in the console.
- **`codeql`** (only while CodeQL host analysis is enabled; the bridge passes the file to `sentra codeql analyze --codeql`, which runs it): the file `SENTRA_CODEQL_BIN` names, when the host operator sets it; no other `codeql` is then run. Otherwise chosen like `gh`: the process PATH or the persisted PATH, never a standard install location or a path set in the console, and on Windows only `codeql.exe`. In both cases the file must also pass the launcher rules of [`SENTRA_CODEQL_BIN`](#configuration) (inside a CodeQL distribution; a `codeql` launcher script is accepted on macOS and Linux). The *codeql* row and *Settings → CodeQL* name the file, or why none qualifies.

Programs the bridge starts, such as the core CLI and through it plugin adapters, look tools up on the bridge's own process PATH, not at the paths shown on this page, including paths set in the console. The exception is CodeQL host analysis, which receives its launcher explicitly as described above.

#### Bun runtime

`bun run` prepends a temporary `bun-node-<hex>` directory inside the system temp directory, holding entries named `bun` and `node`. Detection skips these shim directories. The *bun* row and the *Bun runtime* field show the located installation that is the same file as the running executable, compared by device and inode rather than by path string:

- On Windows the shim entries are hard links, and `process.execPath` names the shim; the row shows the install it links to (for example `~/.bun/bin/bun.exe`).
- On macOS and Linux the shim entries are symlinks, and `process.execPath` is already the resolved file, for example `/opt/homebrew/Cellar/bun/<version>/bin/bun` for a Homebrew install. The row shows the `PATH` entry (`/opt/homebrew/bin/bun`) with the resolved file as its symlink target.
- With Scoop, the located `~\scoop\shims\bun.exe` is a shim copy, so its `.shim` target (`~\scoop\apps\bun\current\bun.exe`) is compared instead; the row shows the shim with that target.

If no located `bun` is the same file (the `bun run` shim is a copy, or Bun was started from outside the searched directories), no other installation is substituted: the row shows the running file, and when that is a shim, a note says the install path is unknown.

### Tool paths set in the console

When automatic detection misses a tool, or finds an installation you do not want reported, a SecurityAdmin (`settings:write`) can set its path in the tools table on *Host & workers*: *Set path* for a tool that was not found, *Change* for one that was, and *Reset to automatic* to remove a path set there. Other roles see the table without these actions. The same operations are `PUT /api/system/tools/:name` with the body `{"path": "<path>"}` and `DELETE /api/system/tools/:name`; both return the tool's updated row (`{tool, warning}`). An unknown tool answers `404`, `gh`, `codeql` and `bun` answer `409`, and a refused path answers `400` (`invalid_tool_path`) with the reason.

- **Which tools.** `git`, `cargo`, `semgrep`, `osv-scanner` and `docker`: tools the bridge never runs. The path of `gh`, `codeql` and `bun` cannot be set (`PUT` and `DELETE` answer `409`): the bridge runs `gh`, runs `codeql` through the core when CodeQL host analysis is enabled, and runs on `bun`, and a path entered in the web console must never become a program the bridge runs. The legacy bridge's command execution through client-supplied paths was a critical issue. To choose the `gh` the bridge runs, the host operator sets `SENTRA_GH_BIN` (see [Configuration](#configuration)); alternatively, store a GitHub token in *Settings → GitHub*, which makes `gh` unnecessary. To choose the `codeql`, the host operator sets `SENTRA_CODEQL_BIN`. A `codeql` path stored in the console by an earlier bridge (contract 4 and before) is ignored: the *codeql* row says so, and the entry is dropped the next time a tool path is saved. The `bun` row is always the running executable.
- **What is accepted.** An absolute path to the executable, or to the folder that contains it. In a folder the tool is looked for under the names automatic detection uses: on Windows the `PATHEXT` extensions, on macOS and Linux with execute permission, and for `osv-scanner` also the release-asset names such as `osv-scanner_windows_amd64.exe` or `osv-scanner_darwin_arm64`. When the folder holds no match but its `<tool>` or `bin` subfolder does, the error names that subfolder.
  - The path is trimmed, and one pair of surrounding double quotes (as Windows Explorer's *Copy as path* adds) is removed. It must be at most 1024 characters, as entered and as stored (after `~` is expanded), without control characters.
  - Windows: a path starting with a drive letter, such as `C:\Tools\semgrep` or `C:\Tools\semgrep\semgrep.exe`. UNC (`\\server\share`) and device (`\\?\`, `\\.\`) paths are refused without touching them, because checking them would make the bridge authenticate to another computer. So are drive-relative forms (`C:tools`), `%VAR%` references and characters Windows does not allow in file names. A file must have a `PATHEXT` extension; `.cmd` and `.bat` are accepted, because nothing is run.
  - macOS and Linux: a path starting with `/`. A leading `~` or `~/` is expanded to the home directory of the user the bridge runs as; `~user` and `$VAR` are not expanded. The file must be executable by that user.
  - The path must exist and lead to a regular file or a folder after links are followed.
  - A file whose header says it cannot run on this host (see [Platform check](#platform-check)) is refused; the message names what the file is built for and what the host is.
  - A file whose name does not look like the tool is saved with a warning, which the console shows before closing the dialog.
- **Nothing is run.** The bridge only checks the path: it lists at most the entered folder and two of its subfolders, and reads at most 64 KiB of the file's header.
- **Time limits.** Each file-system call of a check (status, listing, permission, header read) must answer within 2 seconds, and a whole check within 5 seconds. A path on a slow or unreachable drive, mapped network drive or NFS/SMB mount is refused, or reported as broken, with "did not answer within …" instead of holding the request; a folder that does not answer is not reported as empty. A call that never returns (an NFS hard mount, for example) is waited on by later checks instead of being started again.
- **When it is checked.** On every save, and then once per tool search refresh (about every 60 seconds): the tools table, *Settings → System* and topology reports of the same refresh share one check instead of touching the file system on every request.
- **Where it is used.** For reporting only: the tools table, *Settings → System* and the tools in topology reports. It is never used to run anything: the `gh`, `codeql` and `sentra` lookups ignore it, and programs the bridge starts (the core CLI, plugin adapters) still look tools up on the bridge process PATH.
- **Storage and audit.** One bridge-wide setting in `sentra-web.db`, the same for every workspace. Each change is recorded in the operator audit log as `tool_path_configured` or `tool_path_cleared`, with the tool and the path; a refused path is recorded as a failure.
- **When the path stops working.** If the file is later removed, its drive stops answering, or it no longer passes these checks, the row is marked *configured path broken* with the reason at the next refresh, and shows what automatic detection finds instead (with the "cannot run here" warning when that file is built for another platform). The stored path is kept until it is changed or reset.

### Platform check

Tool rows do not show architectures; the bridge reads the file header of each match, and of the `sentra` binary, only to decide whether the file can run on this host. Nothing is executed:

- **PE** (Windows): the COFF machine type.
- **ELF** (Linux): `e_machine`.
- **Mach-O** (macOS): the CPU type. A universal (fat) binary lists every architecture it contains.
- **Scripts:** files that start with `#!` are treated as scripts, which run through their interpreter.

The result is compared with the host's native architecture:

| Result | Meaning |
| --- | --- |
| native | Matches the hardware. |
| emulated | Runs under emulation, for example an x64 binary on Windows on Arm, or under Rosetta 2 on Apple silicon. |
| 32-bit | Runs through a 64-bit OS's 32-bit compatibility layer: x86 under WOW64 on Windows (also on Windows on Arm), i386 on Linux x64, and 32-bit Arm on Linux arm64, which runs only if the CPU and kernel support AArch32 (many arm64 servers and boards do; some recent cores do not). |
| incompatible | Cannot run on this host: built for another OS, or for an architecture this host cannot run. This includes 32-bit Arm on Windows on Arm (Windows 11 24H2 and later do not run 32-bit Arm apps) and any 32-bit code on macOS. |
| unknown | The header was not recognised or could not be read, for example a Windows App Execution Alias. |

Only *incompatible* is shown: the tool's status reads "found, but built for another platform — cannot run here" (the core CLI card says the same for the `sentra` binary; a row whose console path is broken says it for the file shown instead), and the status tooltip names the format, the architectures the file is built for and the reason. The same rules refuse such a file as a [tool path set in the console](#tool-paths-set-in-the-console), and decide which architecture-suffixed release assets (such as `osv-scanner_linux_arm`) count as present; none of those tools is run by the bridge.

### Host fields

| Field | Windows | macOS | Linux |
| --- | --- | --- | --- |
| OS name | `os.version()`; "Windows 10" becomes "Windows 11" on build 22000 or later, because Windows 11 keeps the old product name in the registry | `sw_vers` product name and version | `PRETTY_NAME` from `/etc/os-release`, else `/usr/lib/os-release` |
| Native architecture | `PROCESSOR_ARCHITECTURE` from the registry, else `PROCESSOR_ARCHITEW6432` / `PROCESSOR_ARCHITECTURE` from the environment | `sysctl.proc_translated` (Rosetta 2) and `hw.optional.arm64` | `os.machine()` |
| Available memory | `os.freemem()` (available physical memory) | `vm_stat` page counts | `MemAvailable` from `/proc/meminfo` |
| Load average | not reported | `os.loadavg()` | `os.loadavg()` |

The *Architecture* field shows the process architecture (`os.arch()`). When the process runs under emulation (Windows on Arm, Rosetta 2), "(emulated on arm64)" is appended. The native architecture is otherwise used only for the [platform check](#platform-check). On macOS, `os.freemem()` counts only free pages, so it would overstate memory use.

## Plugin directory

The *Plugins* tab, its probe and run actions, and the console's `plugins` command use one plugin directory, chosen in this order:

1. **`SENTRA_PLUGIN_DIR`** from the bridge environment. The bridge refuses to start when it is set but is not an existing directory. Changing it requires a restart.
2. **The core's platform default directory.** The bridge does not compute it. On the first listing it runs `sentra plugin list --json` without `--dir` and uses the directory the core reports. That run passes the variables the core reads on the bridge's platform from the bridge environment (`APPDATA` on Windows, `HOME` on macOS, `XDG_CONFIG_HOME` and `HOME` elsewhere), but not `SENTRA_PLUGIN_DIR`. It only reads manifests; no adapter is started. The core's rule is `%APPDATA%\sentra\plugins` on Windows, `$HOME/Library/Application Support/sentra/plugins` on macOS, and `$XDG_CONFIG_HOME/sentra/plugins` (or `$HOME/.config/sentra/plugins`) elsewhere. It only uses absolute values. The bridge keeps the answer until it restarts. A failed query (core missing, busy or timed out) is retried on the next listing, and so is a check that did not answer in time (below), in which case the core is not asked.
3. **None.** The listing says why, and probe and run answer `412 plugins_not_configured`.

The bridge refuses a platform default directory when either of these applies:

- it is not an absolute path: on Windows, a path that starts with a drive letter (UNC and device paths are refused); elsewhere, a path that starts with `/`;
- on Windows, its real path (links, junctions and mapped drives resolved, as far as the host's `realpath` reports them) is a UNC or device path, or cannot be determined within 2 seconds;
- it is inside, or contains, the bridge data directory, the bridge temporary directory, the system temporary directory, the repository checkout or a registered workspace. Both the reported path and its real path (with links and junctions resolved) are compared.

Network mounts on macOS and Linux (NFS, SMB) are not detected: a default directory on such a mount is accepted. On Windows the detection of a mapped network drive or a link to a share relies on the real path being reported in UNC form; it is unit-tested with injected real paths only, as no mapped network drive was available on the test host.

A refused directory is reported as none, with a `plugin_dir_refused` diagnostic. On Windows, `APPDATA` is not passed to the core when it is a UNC or device path (for example under Folder Redirection), or when the real path of `<APPDATA>\sentra\plugins` (or of its nearest existing ancestor) is one, so the core does not open the share (`plugin_dir_network_path`). When that check does not answer within 2 seconds (an offline network drive, for example), the core is not asked and the listing reports `plugin_dir_not_answering`. `HOME` and `XDG_CONFIG_HOME` are not checked or reported on Windows, because the core does not read them there. Every real-path and existence check runs asynchronously with a 2-second deadline, and a check still pending for the same path is joined instead of started again. The bridge re-checks these rules on every listing, so registering an overlapping workspace stops the directory from being used. They do not apply to `SENTRA_PLUGIN_DIR`, which the host operator sets explicitly.

The bridge never creates the directory. It checks that the directory exists on every listing, and does not run the core while it is missing. A directory created later, with one subdirectory holding a `manifest.json` per adapter, is picked up without a restart. One core run serves listings for up to 15 seconds. *Rediscover* (`GET /api/plugins?refresh=1`) and the listing that probe and run make before they start the adapter never reuse a completed run: they start a new one, or join one that is still running.

`GET /api/plugins` returns these fields:

- `directory`, `directorySource` (`environment`, `platform_default` or `none`) and `directoryExists`;
- `diagnostics`, `hasErrors` and `hint`;
- `configured`, which is true whenever a directory is in use, even before it exists;
- `pluginDir`, a deprecated alias of `directory`.

Diagnostics from `sentra plugin list` are passed through with their severity, code, message and path. Examples are `manifest_invalid_json`, `manifest_invalid`, `duplicate_plugin_id` and `nested_manifest_ignored`. The bridge adds `plugin_dir_*` diagnostics about the directory itself. It also adds `plugin_entry_ignored` for listed entries it drops: a manifest outside the directory, or an entry without an id.

Unlike [tool paths](#tool-paths-set-in-the-console), the directory cannot be set in the console. Adapters in it are started as programs on the bridge host, without a sandbox.

The following is unit-tested with a stubbed core: the resolution order, the environment handed to the core (for Windows, macOS and Linux), the refusal rules for Windows, macOS and Linux paths (with an injected platform and injected real paths, including real paths on a share), the 2-second deadlines and the joining of pending checks (with never-answering injected probes), the routes (including the fresh listing of *Rediscover*, probe and run), and the console's handling of the contract 3 response shape. On the Windows 11 x64 host, tests also ran against the real core binary:

- a temporary `APPDATA` gives `<APPDATA>\sentra\plugins`;
- without `APPDATA` there is no default;
- a temporary default directory created after the first listing is picked up. It held a valid manifest, an invalid one, and two manifests with the same id.

The CI `web-test` job does not build the core, so these real-binary tests are skipped there. The core's macOS and Linux default directories have not been checked through the bridge on a real host. The Plugins tab has not been tested in a browser.

## CodeQL

CodeQL results reach the console in three ways. Importing results is always available; running CodeQL on the bridge host is off until a SecurityAdmin enables it. The decision and its security review are recorded in [ADR-0011](../docs/adr/0011-opt-in-host-codeql-analysis.md), which narrowly supersedes [ADR-0004](../docs/adr/0004-vm-boundary-for-untrusted-execution.md) for CodeQL with build mode `none` only.

| Origin | How | Permission |
| --- | --- | --- |
| `host_analysis` | The CodeQL stage of a scan runs `sentra codeql analyze` on the bridge host. | `scan:run` to start the scan; enabling host analysis needs `settings:write` |
| `sarif_import` | *Findings → Import CodeQL SARIF*: a SARIF file produced elsewhere (a local CodeQL run, GitHub Actions) is parsed by `sentra codeql import`. | `scan:run` |
| `github_code_scanning` | *Findings → Sync GitHub code scanning*: open alerts of tool CodeQL for the workspace's repository, read from the GitHub API. | `scan:run` |

### Host analysis

**Enabling.** *Settings → CodeQL* (`PUT /api/settings/codeql`, `settings:write`). The request that sets `enabled: true` must also carry `acceptTerms: true`; otherwise it answers `400 codeql_terms_required`. The console shows a summary of the conditions of the GitHub CodeQL Terms and Conditions, the location of the authoritative text (`LICENSE.md` in the root of the CodeQL distribution; on a host with a launcher the page names that file) and a checkbox. Who accepted the terms and when is stored with the setting and in the audit entry `codeql_settings_updated`, which records every change, refused ones included. Disabling keeps the record; enabling again requires accepting again. `GET /api/settings/codeql` (`read`) returns the settings, the launcher that would be run (or why none qualifies), the pack cache, whether and why a scan would not start host analysis now, and the analysis currently running.

| Setting | Default | Bounds |
| --- | --- | --- |
| `enabled` | `false` | requires `acceptTerms: true` in the same request |
| `allowPackDownload` | `false` | when true, missing query packs are downloaded from GitHub's container registry (ghcr.io) into the pack cache |
| `suite` | `code-scanning` | `code-scanning` or `security-extended` |
| `timeoutMinutes` | 30 | 5–180 |
| `threads` | min(4, logical CPUs) | 1–logical CPUs of the bridge host |
| `ramMb` | unset (CodeQL's default) | 1024–total memory of the bridge host |

Set `ramMb` on a host that runs other memory-hungry programs. On the Windows 11 x64 development host (32 GB RAM, about 5.7 GB of commit memory free) on 2026-11-11, CodeQL 2.27.4 without `--ram` failed in `codeql database analyze` (its Java VM could not commit memory, Windows error 1455; another run printed "CodeQL is out of memory", exit 99), and the same analysis with `ramMb` 2048 completed. The core names this failure in the language's reason, and the stage message then points at this setting, both when every language failed and when other languages were analyzed.

**What the CodeQL stage does.** The language probe (`sentra codeql --workspace <ws> --json`) always runs. Host analysis then runs only when it is enabled with accepted terms, the core binary is present, a launcher qualifies (see [Which file is run](#which-file-is-run)) and no other CodeQL analysis is running on the bridge: at most one runs bridge-wide at a time, and a second scan reports its analysis as skipped. The command is:

```
sentra codeql analyze --workspace <ws> --codeql <launcher> --work-dir <data dir>/tmp/codeql-<random>
  --pack-cache <data dir>/codeql-packages --accept-codeql-terms --suite <suite> --threads <n>
  --timeout-secs <minutes * 60> --max-results 5000 [--ram <MiB>] [--allow-pack-download]
  --cancel-on-stdin-eof --json
```

The bridge creates the work directory under its private temporary directory, outside every workspace, and removes it afterwards; the pack cache is inside the data directory, never `~/.codeql`. The bridge stops the core itself only after the CodeQL timeout plus 120 seconds. The core enforces the rest (ADR-0011): build mode `none` only (no autobuild, no build command, no tracing), the allow-listed environment, one total time budget (the `codeql version` step is also capped at 120 seconds; the other steps share the budget), killing CodeQL's process tree on timeout and on cancellation, bounded output and deletion of the temporary databases. On Windows it refuses a workspace whose path contains `&`, `^`, `!` or `%` (`invalid_workspace`, a failed stage), because CodeQL's extractor batch scripts expand the source directory unquoted and `cmd.exe` would run part of the path as a command; such a workspace can still import SARIF. The bridge discards the results unless the core reports `target_code_executed: false`.

The stage message always says what happened. Host analysis did not run, or produced no results, for these reasons; the stage still completes with the language probe:

| Reason | Meaning |
| --- | --- |
| `disabled` | Host analysis is off (the default). |
| `terms_not_accepted` | No acceptance of the terms is recorded. |
| `core_unavailable` | The `sentra` binary is missing. |
| `launcher_unavailable` | No `codeql` launcher qualifies; the message names the file and the rule it fails. |
| `analysis_busy` | Another analysis is running on the bridge. |
| `packs_missing` | The query packs are not in the pack cache and pack download is off. The CodeQL CLI-only distribution ships no query packs; allow pack download, or install the CodeQL bundle. |
| `languages_need_build` | The core skipped every detected language: it needs a build (`go` and `swift` have no build mode `none`), or, as the core reports for `rust`, `csharp` and `java`, its build-mode-`none` extractor would run project code. Sentra does not build projects or run their code on the host. The per-language reasons are shown. |
| `no_languages` | CodeQL found no language it can analyze. |

A failed analysis (`codeql_failed`, `codeql_timeout`, `codeql_not_found`, `codeql_cancelled`, `invalid_workspace`, a timeout of the bridge, or a report that does not state `target_code_executed: false`) fails the stage, and nothing is stored from it. The run's summary keeps the outcome (`summary.codeqlAnalysis`, with `outcome` `analyzed`, `skipped` or `failed`), which the scan view shows; a run whose analysis failed does not count as a run with results (for *Last scan with results* and the risk score), even when its other stages completed.

A host analysis holds one of the bridge's core process slots (`SENTRA_CLI_MAX_CONCURRENCY`, default 2) for its whole run, up to the CodeQL timeout plus the bridge margin. With the default, a second scan's CodeQL stage is reported as `analysis_busy` at once; with `SENTRA_CLI_MAX_CONCURRENCY=1`, every other core call waits behind the analysis instead, so keep at least 2 slots when host analysis is enabled.

While CodeQL runs, the core prints nothing on the scan stream for minutes at a time. The bridge writes an SSE comment line (`: keep-alive`) every 15 seconds so that a reverse proxy in front of the bridge does not close the stream for inactivity (nginx's default `proxy_read_timeout` is 60 seconds); a closed stream cancels the scan.

**Isolation.** No target code is executed, but CodeQL's extractors parse the untrusted workspace code on the bridge host, outside the VM boundary of ADR-0004. Process separation is not containment. When a scan is cancelled, the bridge closes the core's standard input (`--cancel-on-stdin-eof`) instead of stopping it; the core then kills the running CodeQL step's process tree (a kill-on-close job object on Windows, the step's process group on macOS and Linux, which a signal to the core would not reach) and exits, and only then does the bridge release the one-analysis lock and remove the work directory. If the core has not exited 30 seconds after its input was closed, the bridge kills it; on macOS and Linux the current CodeQL step may then keep running. The pipe also closes when the bridge process dies, so the core stops CodeQL in that case too. Tested on 2026-11-11 on Windows 11 x64 with a fake CodeQL (core contract test), with a stand-in core (bridge test), and with CodeQL CLI 2.27.4 by closing the stdin of `sentra codeql analyze --cancel-on-stdin-eof` during `codeql database analyze` (the core exited 0.07 s later and no process from the CodeQL distribution was left 3 seconds later); an earlier bridge version's cancellation (stopping the core) also left no process from the distribution on Windows. macOS and Linux have not been tested with a real CodeQL.

### Import a CodeQL SARIF

`POST /api/tenants/:id/codeql/import` (`scan:run`) takes the SARIF document itself as the request body with `Content-Type: application/json`. This route alone accepts up to 64 MiB (`413 sarif_too_large` beyond that); every other route keeps `SENTRA_WEB_MAX_BODY_BYTES`. The console reads the chosen file in the browser and posts its text. One import is processed at a time on the bridge; a second one is refused with `429 codeql_import_busy` before its body is read. The bridge streams the body into a private file under `<data dir>/tmp` without holding it in memory. An empty body, or one that does not start like a JSON object, is refused (`400 sarif_invalid`); a body of up to 256 KiB is also parsed by the bridge, which then refuses one that is not a SARIF log with runs (`400 sarif_invalid`) or has a run whose `tool.driver.name` is not CodeQL (`400 sarif_not_codeql`) without starting the core. Larger bodies are not parsed by the bridge, because a full parse of a 64 MiB document would cost far more memory than the file; the core checks them (same error codes) in one bounded streaming pass. The bridge runs `sentra codeql import --sarif <file> --workspace <ws> --max-results 5000 --json` and deletes the file. Results whose path is absolute or leaves the workspace are dropped and counted. Each import is recorded as `codeql_sarif_imported`.

Importing again resolves the earlier imported findings of the rules the new file ran that it no longer reports. CodeQL lists every query it ran in the SARIF, also queries without results, and the core reports these rules per language, so a file whose results are all gone still resolves the findings of its rules. Findings of rules the file did not run (another query suite, another language), of host analysis and of GitHub code scanning are not touched, and a truncated result list resolves nothing. A SARIF that lists no rules resolves only findings of the rules it has results for.

### Sync GitHub code scanning

`POST /api/tenants/:id/codeql/github-sync` (`scan:run`) needs a GitHub credential and the workspace's repository (configured for the workspace or detected from its `origin` remote; otherwise `412 github_not_configured` or `412 repository_not_resolved`). It reads `GET /repos/{owner}/{repo}/code-scanning/alerts?tool_name=CodeQL&state=open&per_page=100&page=N` through the bridge's GitHub client (with its time and size limits), up to 10 pages (1000 alerts). It writes nothing to GitHub. Each alert becomes a finding identified by repository and alert number:

- severity from `rule.security_severity_level` (critical, high, medium, low), else from `rule.severity` (error → Medium, warning → Low, note → Informational);
- CWE ids from `external/cwe/cwe-NNN` tags, the location and message of `most_recent_instance`, the alert's web URL, its number and the tool version.

The alert paths are repository-relative and are matched to the workspace as they are; the local checkout may differ from the analyzed commit. Alerts that are no longer open are resolved at the next sync, but only for the same repository and only when the listing was complete. When ten full pages are read, the bridge requests an eleventh page only to see whether more alerts exist: exactly 1000 open alerts are complete, more than that are truncated (the first 1000 are stored and nothing is resolved). `403` answers `github_code_scanning_forbidden`: code scanning or GitHub Advanced Security is not enabled for the repository, or the credential lacks access (a classic token needs the `security_events` scope, or `public_repo` for public repositories; a fine-grained token needs the *Code scanning alerts: read* permission). `404` answers `github_code_scanning_not_found`. Each sync is recorded as `codeql_github_synced`.

### CodeQL findings

CodeQL findings have the source `codeql` and one of the three origins, and each (workspace, source, origin) is reconciled on its own: a SARIF import never resolves a host-analysis finding, and the reverse. Host analysis resolves only findings of the rules it ran in that run (switching *Settings → CodeQL* from `security-extended` to `code-scanning` leaves the findings of queries that only `security-extended` runs open, instead of counting them as fixed). Fingerprints combine CodeQL's line hash with its start-column fingerprint, so two results of one rule on one line are two findings; findings stored with the earlier line-hash-only fingerprint are resolved once and stored again by the next analysis or import. Because each origin is stored on its own, one CodeQL result reported by host analysis, a SARIF import and GitHub code scanning counts once per origin in the open total, the severity counts, the risk score, the executive report and the SARIF export; the overview and the executive report show the CodeQL count per origin (`openFindings.codeqlByOrigin`). Severity follows GitHub's thresholds for `security-severity` (>= 9.0 Critical, >= 7.0 High, >= 4.0 Medium, > 0 Low); without it, `problem.severity` error maps to Medium, warning to Low, and recommendation or note to Informational. The *Findings* tab filters by source and, for CodeQL, by origin; the detail view shows the origin, language, query metadata, tool version, query help and, for GitHub alerts, a link to the alert. Model patch candidates are not offered for CodeQL findings. The SARIF export includes open CodeQL findings with their origin as a property, and the executive report counts them.

What has been tested: unit and route tests with a stubbed core that prints the JSON of the `sentra codeql analyze|import` contract and with injected GitHub responses. They cover the settings routes and their roles and audit entries, the terms gate, the single-analysis lock, every skip reason, the command line and work directory clean-up, import validation and limits, alert mapping, pagination, truncation, `403`/`404`, reconciliation scoping, the database migration, and that a `codeql` path stored in the console never becomes the launcher. On 2026-11-11, on the Windows 11 x64 development host, the HTTP routes (called in-process through `handleRequest`, with a temporary data directory and generated tokens; no port was bound) also ran against a release build of the core and CodeQL CLI 2.27.4 (`SENTRA_CODEQL_BIN` pointing at its `codeql.exe`), on a small Express fixture with a reflected XSS and a SQL injection plus a Go file:

- Import of the SARIF written by `codeql database analyze` for that fixture: 3 findings stored with origin `sarif_import` (0.7 s); importing the same file again created nothing and kept the 3 open.
- Host analysis through a scan's CodeQL stage, with host analysis enabled (terms accepted, pack download allowed, `ramMb` 2048, the pack cache pre-filled with `codeql/javascript-queries` 2.5.0): javascript analyzed with 3 results (`js/reflected-xss`, `js/sql-injection`, `js/missing-rate-limiting`, all High), go skipped as needing a build, 39 s; findings stored with origin `host_analysis` next to the imported ones, and a second scan created nothing. A scan of a second workspace started while the first analysis ran reported `analysis_busy` without starting CodeQL. Without `ramMb` the analysis failed for lack of memory on this host (see the settings above).
- GitHub sync with an injected HTTP client (no real GitHub request): 2 alerts stored with origin `github_code_scanning`; one GET request; after one alert disappeared from the listing it was resolved and nothing else changed.
- The overview counted the 7 open CodeQL findings under `codeql`, the SARIF export contained them, the audit chain verified, the bridge temporary directory was empty after every step, and no `~/.codeql` was created.

Not tested: the real GitHub API, the *Settings → CodeQL* section and the *Findings* actions in a browser, and macOS or Linux hosts.

## Limitations

- SAST is the core's heuristic, line-based rule set. Findings are candidates until a human triages them.
- CodeQL host analysis, when enabled, has CodeQL's extractors parse untrusted workspace code on the bridge host (build mode `none`; no target code is executed). See [CodeQL](#codeql) and ADR-0011.
- Patches are model-generated and are only dry-run checked. No tests run, because the core has no isolated verifier.
- PR scans cover only the files changed at the PR head commit.
- Webhook scans run against the local checkout. The bridge never fetches or pulls. Each delivery's detail says whether the local `HEAD` matches the pushed commit.
- Plugin adapters run as unsandboxed subprocesses on the bridge host. The core enforces their time limit and frame and output quotas; their declared egress policy and memory quota are not enforced. Without `SENTRA_PLUGIN_DIR`, the platform default plugin directory is resolved once per bridge process; see [Plugin directory](#plugin-directory).
- When a plugin session ends, the core kills the adapter's process tree. On Windows a Job Object contains every descendant. On a Linux or macOS bridge host the core kills the adapter's process group and the processes that carry the session's `CONTAINED_BY_SENTRA` environment value (which the core adds to the adapter's environment) or descend from the adapter; a detached descendant (`setsid`) that was started without that variable, or on macOS whose environment the kernel withholds (code-signing-restricted binaries while System Integrity Protection is on), survives once its parent has exited. On other Unix hosts only the process group is killed. See [docs/LIMITATIONS.md](../docs/LIMITATIONS.md#6-web-console-and-pinned-core-commands) (section 6, item 5).
- There is no remote worker fleet: the core has no persisted worker registry.

### Bridge and console versions

`bun run dev` hot-reloads the console when `src/` changes, but the bridge (`server.ts`) keeps running the code it started with. To make that visible, `src/types/api.ts` defines `API_CONTRACT_VERSION`, which the bridge reports as `apiContractVersion` in `GET /api/health` (public) and `GET /api/system`. The console checks `/api/health` on load, every 30 seconds while visible, and when the window regains focus. When the versions differ, or the bridge reports none (it predates version 2), a banner says which side is older:

- **Bridge older than the console** (it was not restarted after an update, or after `bun run build` in production): the banner asks you to restart the bridge (stop it and rerun `bun run dev`, or `bun run start`).
- **Bridge newer than the console**: the banner asks you to reload the page. If the banner stays, in production (`bun run start`) the console is the prebuilt `web/dist`, which a reload serves unchanged, so rebuild it with `bun run build` and reload; in development, the bridge was started from another checkout, so restart it from this one.

Views whose data has the old shape show a "restart the bridge" placeholder, and each tab renders inside an error boundary, so a view that still fails shows the error instead of a blank page.

Bump `API_CONTRACT_VERSION` whenever a response shape changes incompatibly: a field is removed, renamed or changes type, or the console starts to require a new field.
